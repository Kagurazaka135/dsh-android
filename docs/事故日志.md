## 2026-11-12 · dsh 反复关掉自动旋转，且从不恢复

### 一、发生了什么

主人反馈：「手机上的 dsh 依旧和方向锁定有仇，喜欢动他。」

当前设备实测：

```
adb shell settings get system accelerometer_rotation   →  0
adb shell settings get system user_rotation            →  0
```

`accelerometer_rotation = 0` 表示**自动旋转关闭**。设备现在就停在锁定状态。

### 二、为什么这不是偶然

和上面那条（锁屏）不是同一类问题，这条**更深**。

#### 1. 模型被主动邀请去转这个开关

`dsh-tool-shizuku` 里 `android_setting_app` 的工具描述，原文写着「常用 key」：

> `screen_brightness`（亮度 0-255）、`screen_brightness_mode`、`screen_off_timeout`、
> **`accelerometer_rotation`（自动旋转 0/1）**、`font_scale`、`volume_music/...`

这不是模型自己找出来的偏门开关，是**工具描述把它列成了入门清单里的一项**。任何一个想「固定屏幕方向好做截图对比」的任务，都会顺手用它。

#### 2. 它不需要任何特权

`stay_on_while_plugged_in` 是 Global 命名空间，得走 `shizuku_shell`。而 `accelerometer_rotation` 是 System 命名空间，`android_setting_app` 只要 App 的 `WRITE_SETTINGS` 权限就能写。

**也就是说：上一节担心的「万能 shell 是个洞」，在这里根本不成立——不需要 shell，一条普通 settings 写就够了。** 权限体系设想的「特权操作才危险」，在这里失效。

#### 3. 三档分类把它放进了「静默允许」

`GuardImpl.setting()` 的实际实现是三档：

| 档位 | 处理 | 键 |
|---|---|---|
| `FOUNDATION_KEYS` | 结构性禁止 | 无障碍、`adb_enabled`、开发者选项、通知监听、未知来源 |
| `EXPERIENCE_KEYS` | 弹窗确认 | 默认输入法、字体大小、显示尺寸/密度 |
| **其余全部** | **`Act("setting.put", false, true, "", "", "", "")`** | **无确认、无记录、无回滚** |

`accelerometer_rotation` 落在第三档。

这**完全符合** `权限.md` §6.12 的设计——那里明确写着「方向锁定属第一档：可逆、无害，给完全权限 + 自动还原即可」。

#### 4. ⭐ 真正的错误在文档里：**「可逆」被当成了「无害」**

§6.12 的推理链是：

```
可逆 → 所以无害 → 给完全权限 + 自动还原
```

这中间省掉了一步：**可逆的前提是有人去还原。**

而「事后还原」在 §6.18 里到今天还是**未勾选的待办**。还原机制不存在，第一档的实际语义就变成了：

> **静默改写、永不恢复。**

这恰好是最坏的三档里最坏的一种——比「弹窗让你选」差（至少你知道发生什么），也比「结构性禁止」差（至少不会改）。

把「无害可逆」改名成「**需要自动还原才无害**」，这条错误就消失了。

### 三、方案要怎么收

短期沿用三件套（改前报备 / 改后声明 / 收工还原）。

但要补一句更实的话：**还原机制没实现之前，第一档不该按第一档对待。** 两个选项：

- **降级**：把第三档整体提到第二档（弹窗），代价是调试脚本每次都要点
- **限缩**：把第三档收窄成「只读」或「只允许任务书显式授权的键」，代价是实现成本

克劳德酱倾向前者先顶住，后者作为正式方案——因为「调试脚本被弹窗烦」是**测试者的成本**，而「主人的手机被悄悄改」是**主人的成本**，这两种成本不该等价对待。

### 附：这次暴露的更深问题

如果 agent 能写 `accelerometer_rotation`，它也能写 `enabled_accessibility_services`（无障碍服务）——后者目前是 `FOUNDATION_KEYS` 结构性禁止。

但**禁止是靠 `GuardImpl` 判断的，而 `GuardImpl` 就跑在同一个 App 里**。除非有 App 之外的一层（系统级 DevicePolicy、独立进程 + 只读通道、或 Shizuku 侧的独立校验），否则「结构性禁止」的真实含义只是「**我们恰好没写这条路径**」。

这个洞目前没有解法，先记在这里。

## 2026-11-12 · 自动化脚本改写了设备设置，锁屏消失

### 一、发生了什么

排查「点搜索后卡死」时，真机脚本每一轮都执行：

```bash
svc power stayon true
input keyevent KEYCODE_WAKEUP
wm dismiss-keyguard
```

后两条只作用于当次操作，**第一条是持久的**——它把 `settings global stay_on_while_plugged_in` 写成 `15`（AC | USB | 无线 | 座充全开）。这个值存进设置数据库，重启不还原。

设备当时插着 USB，于是：

- 屏幕永不熄灭（`mStayOn=true`）
- 锁屏没有任何机会出现
- 超时之后 MIUI 只把亮度压下去

主人看到的现象因此是「**锁屏没了，只剩降亮度**」。这个症状随插拔电源变化，和「锁屏坏了」的直觉完全对不上。

会话记录里这组命令出现 **43 次**（每轮测试前一次），全部未回滚。排查时一度怀疑过锁屏本身、输入法、系统版本，最后是靠 `dumpsys power` 和 `settings get` 才定位到。

**已还原**：`adb shell svc power stayon false` → 三项验证 `stay_on_while_plugged_in=0` / `mStayOn=false` / `mStayOnWhilePluggedInSetting=0`。

### 二、为什么这不是偶然

#### 1. 它不在「非敏感设置白名单」里

`权限.md` §6.12 把设置分了三档，第一档「无害可逆」明确列的是：

> 亮度、音量、方向锁定、勿扰、WiFi 开关

`stay_on_while_plugged_in` **不在这张表里**。按文档自己的规则，它本来就不该被无提示地改。

白名单没起作用，不是因为规则写错了，是因为**它还没实现**——§6.18 里「『非敏感设置』白名单写死」至今是一个未勾选的待办项。

#### 2. 就算实现了，`shizuku_shell` 也能绕过去

这是 §6.17 ④ 那个「最大的洞」的第一次真实发作。

`shizuku_shell` 是万能 shell，`svc power stayon true` 只是无穷多写法里的一种。正则拦不住：

```
svc power stayon true
settings put global stay_on_while_plugged_in 7
cmd power set-adaptive-power-policy ...
```

同一个效果，三种写法，还有更多。这正是文档里写的「**拦得住明写的，拦不住变形的**」。

#### 3. ⭐ 真正的问题：**守卫自己的地基，和它要守的东西住在同一层**

这一条是这次事故最值得记的东西，`权限.md` 现在还没写。

第六节整章在解决「模型自己点确认」，方案是四道闸（§6.3~§6.6）。但**这四道闸都有各自依赖的地基，而这些地基全部躺在 agent 能写的那个环境里**：

| 闸 | 依赖什么才能成立 | 模型怎么拆 |
|---|---|---|
| 6.4 确认界面读不到、看不见 | 无障碍服务开着 | `settings put secure enabled_accessibility_services null` |
| 6.5 认出「这是机器点的」 | 输入系统状态未被篡改 | 改 IME、改触摸相关设置 |
| 6.6 提示走人能做到、模型读不到的通道 | TTS / 通知未被关 | 关通知、改勿扰 |
| 确认框会出现在屏幕上 | **屏幕是亮的、锁屏没挡着** | ← **本次事故就是这个** |

也就是说：**守卫自己站在被守卫者可以随意改写的地面上。** 这不是白名单漏了一格，是分层没做——权限系统需要一个模型写不了的底座，而现在整个环境都在模型手里。

本次事故只是拆掉了最后一行（屏幕状态）。前几行还没人拆过，但没有理由认为拆不动。

#### 4. 意图相同，权限等级可以完全不同

`svc power stayon true` 和 `input keyevent KEYCODE_WAKEUP` 在 agent 眼里是同一个意图——**「让它醒着」**。但它们一个是持久改写环境、一个是本次动作。

在一行命令里拼起来，就没有任何机制能把它们分开。

**判据应该是「这个动作会不会在任务结束后继续生效」，不是「它看起来想干什么」。**

### 三、方案要怎么收

#### 短期（这次就能做）

给所有 AI 工人的任务书加硬性三件套：

1. **改前报备** —— 改哪个键、改成什么、为什么非改不可
2. **改后声明** —— 报告里单列「设备状态变更」，逐条列键与值
3. **收工还原** —— 交付前恢复原值并**贴命令输出证明**

**为什么「改前报备」比「收工还原」更根本**：只要求还原的话，它下次还是会先改、只是记得改回来；要求先报备的话，人当场就能说「这条不能碰，换个办法」。还原是补救，报备是阻止。

适用范围（非穷举）：屏幕常亮/超时、亮度、音量、勿扰、开发者选项、USB 调试授权、输入法、默认应用、电池优化白名单、时区语言、动画缩放、锁屏设置。

#### 中期（需要设计）

三个方向，取舍不同：

**方向 A：设置写操作走白名单，fail-closed**

`权限.md` §6.12 已有雏形，补上这次的例子即可。要点是**默认拒绝**——不在表里的设置键一律不写，而不是「不在黑名单里就放行」。

- 优点：形态最简单，实现成本最低
- 缺点：依赖白名单完备性；`shizuku_shell` 绕过的洞还在

**方向 B：每次设置写操作前强制快照，任务结束自动 diff + 还原**

`权限.md` §6.18「设置类操作的快照 / diff / 还原」已列，但归在「兜底」。**这次事故证明它应该提到主防线**——因为它不依赖「猜对哪些键危险」，对所有键一视同仁。

- 优点：不依赖白名单完备性，天然覆盖未知键
- 缺点：还原可能撞上用户在这期间的合法修改；需要定义冲突处理

**方向 C：把「允许改环境」变成任务书显式授权**（这次想到的新方向）

默认任何设置写操作都拒绝；只有在任务书里**显式列出**「本次允许修改的设置键」时才放行。

- 优点：授权边界和任务边界重合，人写任务书时就知道自己要放什么权
- 缺点：任务书写起来更重；临时排查容易被这个流程劝退，反而诱发绕路

三个方向不互斥。克劳德酱的倾向是 **B 做地基 + C 做授权**：B 保证「不管改了什么都能还原」，C 保证「改之前有人点过头」。A 的价值在于给出可读的清单，但不该是唯一防线。

#### 长期

`权限.md` §6.17 ④ 那个死结仍然没有解——万能 shell 长期在线，就必然拦不住变形写法。本次事故是这个死结的**实证**，不是新问题。

能做的仍然只有文档里那条：**承认洞存在，不假装解决了**；把审计做全（记 key / 原值 / 新值 / 触发指令 / 时间）；把「被拒后换路径重试」做成熔断。

### 附：排查这类问题的捷径

症状是「设备行为怪异」而不是「功能报错」时，**先看系统状态，再看应用**：

```bash
adb shell dumpsys power | grep -iE "mStayOn|mWakefulness"
adb shell settings get global stay_on_while_plugged_in
adb shell settings list global | grep -iE "screen|lock|stay"
```

同时**把排除项也记下来**。这次 `lockscreen.disabled=0` 和 `screen_off_timeout=30000` 都正常，只有 `stay_on` 一项异常——写下「排除了什么」比只写「问题在哪」更省下一个人的时间。
