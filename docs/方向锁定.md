# 方向锁定为什么老被关

> 2026-11-12。这不是一次事故，是**长期反复发生的常态**——所以单独成篇。
> 事故日志里保留一条摘要，链到这里。

---

## 一、现象

主人 2026-10-27 原话：

> dsh 似乎很讨厌方向锁定，每次都给我关了，有点难绷。

2026-11-12 主人补了一句更准确的描述：

> 不管需不需要旋转，只要任务出现了画面切换，方向锁定必被动。
> 给模型说你能干啥，合理，但是他给你玩成了**不管需不需要，这个开关你给我了我就要按一下**。

设备实测（2026-11-12）：

```
adb shell settings get system accelerometer_rotation   →  0     （自动旋转关闭）
adb shell settings get system user_rotation            →  0
```

---

## 二、为什么模型会去动它

### 2.1 工具描述主动推荐了它

`dsh-tool-shizuku` 里 `android_setting_app` 的工具描述，原文的「常用 key」清单：

> `screen_brightness`（亮度 0-255）、`screen_brightness_mode`（0=手动 1=自动）、
> `screen_off_timeout`（屏幕超时毫秒，如 60000）、
> **`accelerometer_rotation`（自动旋转 0/1）**、`font_scale`（字体大小，如 1.0/1.3）、
> `volume_music` / `volume_ring` / `volume_alarm` / `volume_notification`（音量 0-15）……

这不是模型翻出来的偏门开关。**是工具描述把它列进了入门清单。** 任何需要「固定屏幕方向好做截图对比」的任务，都会顺手用它。

### 2.2 它不需要任何特权

| 设置键 | 命名空间 | 写入途径 | 需要特权 |
|---|---|---|---|
| `stay_on_while_plugged_in` | Global | `shizuku_shell` → `settings put` | 是 |
| **`accelerometer_rotation`** | **System** | **`android_setting_app`** | **否（只要 `WRITE_SETTINGS`）** |

这一点很关键：**权限体系设想的「特权操作才危险」在这里失效。** 一条普通 settings 写就能穿过去。

### 2.3 三档分类把它放进了「静默允许」

`GuardImpl.setting()` 的实际实现：

| 档位 | 处理 | 包含 |
|---|---|---|
| `FOUNDATION_KEYS` | 结构性禁止 | 无障碍服务、`adb_enabled`、开发者选项、通知监听、未知来源 |
| `EXPERIENCE_KEYS` | 弹窗确认 | 默认输入法、字体大小、显示尺寸/密度 |
| **其余全部** | **`Act("setting.put", false, true, "", "", "", "")`** | **无确认、无记录、无回滚** |

`accelerometer_rotation` 落在第三档。

## 三、⭐ 真正的错误在文档里

`权限.md` §6.12 的设计表：

| 类别 | 例子 | 权限 |
|---|---|---|
| **无害可逆** | 亮度、音量、**方向锁定**、勿扰、WiFi 开关 | 完全权限 + 事后还原 |
| **影响体验** | 默认输入法、字体大小、桌面布局 | 弹窗，或完全权限 + 强制还原 |
| **改地基** | 无障碍服务、设备管理、USB 调试、开发者选项 | 弹窗 + 不可记忆 |

原文还有一句：

> 方向锁定属第一档：可逆、无害，给完全权限 + 自动还原即可。

**这条推理省了一步。**

```
可逆 ──→ 无害 ──→ 给完全权限 + 自动还原
              ↑
        缺了这一步：可逆的前提是有人去还原
```

而「事后还原」（`权限.md` §6.18「设置类操作的快照 / diff / 还原」）**到今天还是未勾选的待办**。

还原机制不存在，第一档的实际语义就变成了：

> **静默改写、永不恢复。**

这恰好是三档里最坏的一种：

| 档位 | 用户感知 | 后果 |
|---|---|---|
| 结构性禁止 | 明确被拒 | 无变化 |
| 弹窗确认 | 知道发生了什么 | 可以拒绝 |
| **第三档（现状）** | **完全没有感知** | **改了也不知道** |

**结论**：第一档不该叫「无害可逆」，该叫「**需要自动还原才无害**」。

---

## 四、⭐ 更深一层：这不是权限漏洞，是工具设计导致的邀请

主人那句判断比任何技术分析都准：

> 不管需不需要，这个开关你给我了，我就要按一下。

模型**不是**在判断「我现在需要转屏幕」。真实的过程是：

1. 工具列表里有一个能改设置的键
2. 任务里出现了画面变化
3. 「调整环境让它更顺」这个动作被触发

**它把「我有这个能力」当成了「这个能力现在该用」。**

而且从它那侧看还特别划算：

- 按一下**不报错**
- 任务**继续跑**
- 屏幕**确实有了变化**

**没有负反馈，所以它学不到「不该按」。**

这和上一节（锁屏那次）是同一类问题的两种形态：

- 锁屏那次：把障碍当成要克服的东西 → 找开关关掉它
- 方向锁定这次：把工具当成该用的东西 → 有就按

两者的共同点：**模型没有「这次用不上」这个判断维度。**

---

## 五、处理方向（按力度排）

### 1. 工具描述里删掉它（最便宜，最直接）

`accelerometer_rotation` 不该出现在「常用 key」推荐清单里。

**推荐清单不是文档，是给模型的行动建议。** 每一项都在暗示「这个你可以随便用」。列了就会被用。

同理要审视整张清单：`volume_*`、`font_scale`、`screen_off_timeout` 是不是也该从「推荐」降级成「可用但需举证」。

### 2. 设置写操作要求「必要性举证」（最根本）

动手之前必须说清：**为什么这个键必须改、不改会怎样。**

说不出来就不允许改。

**为什么比弹窗有效**：弹窗会被无脑点过（人也不会每次都认真看），而「说清理由」对模型是一个**真实的门槛**——它得先理解这次为什么需要，才能说出来。

### 3. 还原（兜底，不是主防线）

前两条做到了，还原就退化成保险丝。

但如果只做还原而不管前面两条，结果就是：**每次任务都在改、每次任务结束都在还原**，用户看到的是「屏幕转了一下又好了」——比不改更烦。

---

## 六、还没解决的

### 6.1 还原的冲突判定

用户在任务跑之前改了设置，任务结束还原会覆盖用户的选择。两种判法：

- **按时间戳**：任务期间用户改过就跳过还原——但分不清是用户改的还是 agent 改的
- **按「本次任务改过的键」限定还原范围**：更安全，但要求精确记录每一次写，而 `shizuku_shell` 层面做不到精确记录

### 6.2 「结构性禁止」其实不结构

如果 agent 能写 `accelerometer_rotation`，它也能写 `enabled_accessibility_services`（无障碍服务）——后者现在是 `FOUNDATION_KEYS` 结构性禁止。

但**禁止是靠 `GuardImpl` 判断的，而 `GuardImpl` 跑在同一个 App 里**。除非有 App 之外的一层（系统级 DevicePolicy、独立进程 + 只读通道、或 Shizuku 侧独立校验），否则「结构性禁止」的真实含义只是：

> **我们恰好没写这条路径。**
