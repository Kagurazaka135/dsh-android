# 写作规范

> 2026-11-12 立。写 README、Release、PR、Issue、提交信息、给别人的文档前先看这个。
> 核心一句话：**能说多少，由受众决定，不由内容重要程度决定。**

---

## 一、判断依据：受众 × 最低认知

**受众规模越大、认知下限越低，一条信息能承载的内容越少。**

不是"内容重要就该说清楚"。说清楚的代价是——**越具体，越容易被截成别的意思。**

三类实证（2026-11-12 整理）：

| 案例 | 缺什么 | 结果 |
|---|---|---|
| 百万塞尔达玩家 | 没玩过（原神 CB1 仅极少数人可玩） | 冒出百万"塞尔达玩家"骂抄袭，得名"百万塞尔达阴兵" |
| 喷白厄剧情 | 跳过了（2026-06-16 实装跳过） | 6-25 第一篇长篇批评版本号都写错，被评论区当场纠错 |
| 喷草神"植物抢空气" | 生物学没学透 | 推理链每一环都是中学生物，一句就自洽，仍被骂 |

共同点：**不是讨论作品，是用关键词输出情绪。** 关键词是"抄袭""剧情烂""抢氧气"，推导过程整个跳过；而且错的人**以为自己站在科学那边**。

## 二、按渠道分级

| 渠道 | 受众 | 写多少 | 失败模式 |
|---|---|---|---|
| **国民级分发**（应用商店更新说明、面向全体用户的通知） | 十几亿人，认知下限极低 | **只写无信息量的一句** | 写多了被截断断章取义 |
| **GitHub Release** | 自己来仓库的人 | 中等：说清修了什么 | — |
| **PR 正文** | 当时的开发者 + 一年后翻 git log 的人 | 中等偏简，标题说清楚 | 太模糊后人查不到 |
| **Issue** | 来查信息/来修的人 | 详细：现象、环境、复现、证据 | 太简看不出根因 |
| **技术文档**（docs/） | 维护者、下一个 AI 工人 | 详细，可引用代码行 | 太简等于没写 |
| **提交信息** | 翻历史的开发者 | 说清"为什么" | 只写"改了啥" |

**注意：这几种渠道的失败模式是相反的。** 国民级渠道怕"太细"，技术文档怕"太简"。用错标准就是两种错。

## 三、具体手法

### 3.1 国民级渠道：只写没有钩子的一句

微信那句「修复了一些已知问题」的全部价值在于**它没说什么**：

- 不含"删除 / 权限 / 自动 / 数据 / 隐私"任何可被单独拎出的词
- 截一半也不成句
- 没有主语、没有对象、没有方向

**这类文字的目标不是"传达信息"，是"占住位置且不受伤"。**

### 3.2 技术文档：反过来，越具体越好

- 带**文件路径 + 行号**，让读者能跳过去
- 带**原始错误输出**，不要转述
- 带**排除项**（"我查过 A、B、C，都正常"）——比只写"问题在 D"更省下一个人的时间
- 带**判据**，不要只给结论

### 3.3 双轨制：梗归 PR，料归 Issue

- **PR 正文**：一句话，可以玩梗（面向愿意点进来的人）
- **Issue 正文**：根因、证据、复现，详尽（面向要修的人）
- 不写 Issue 就把技术内容留在仓库内的报告文件里（如 `docs/事故日志.md`）——**公开面空、自己人查得到**

### 3.4 句子结构：截一半仍然成立

需要写具体内容时，**主语、对象、方向都写死**：

- ❌「修复了删除按钮的问题」→ 抓"删除"，不问修好还是修坏
- ✅「修复了点击删除后无法撤销的问题」→ 截一半也不成句

越短越容易被截成武器；越完整越难被断章取义。

### 3.5 不给自己挖坑的词

写公开面时自查这几个：

| 词 | 风险 |
|---|---|
| 删除 / 清除 / 移除 | 被读成"承认有删除问题" |
| 权限 / 隐私 / 数据 | 被读成"承认有问题" |
| 自动 | 被读成"你替我做了决定" |
| 崩溃 / 丢失 / 失败 | 被读成"承认事故" |

必要时要写，就写**完整的因果**，不要单独出现。

## 四、写任务书时的额外注意

1. **受众是执行者，要写死写细**（见 `权限.md`、`任务书-*.md` 的历史样本）
2. **但任务书本身可能外流**——如果涉及未公开的安全设计（如具体绕过路径），按"可能被公开"的标准裁剪，敏感细节指向仓库内文件
3. **`任务书-*.md` 在 .gitignore 里不公开**（见仓库根 `.gitignore`），路径要求写仓库相对路径

## 五、一页速查

```
写之前先问：这段话会被谁读到？其中认知最低的那部分人会怎么截？

国民级 → 一句无钩子的话就够
GitHub → 说清修了什么
技术文档 → 写细，带路径/行号/原始输出/排除项
PR → 梗可以玩，但正文别模糊
Issue → 详细，标题避开高危词
提交信息 → 写"为什么"，不写"改了啥"
```
