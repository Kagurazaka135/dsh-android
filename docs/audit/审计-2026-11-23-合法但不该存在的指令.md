## 一、Q1 动作来源校验

**结论：搜遍执行链，没有任何一处校验「这个动作有没有对应的用户指令」。**

逐项证据：

1. **dialog_id 不是来源校验，是回调路由**。`dh0/s0.smali:1250-1252` 把 dialogId 作为 key 放进 `Map.put(dialogId, action)`——用途是把执行结果路由回对应会话。AICR 侧执行器 `d.smali`（smali_classes3/.../actionprovider/d.smali，全文件 14218 行）与 voiceassist 的 `hp/a.smali` 中 `dialog_id`/`dialogId` **字符串零命中**——下游执行层根本不知道这个动作来自哪个对话。
2. **utterance/query 与动作的关联：零命中**。在 `classes7/dh0`、`classes7/cb0`（Operation 全包）、`classes19/hp`（ActionManager）中搜 `utterance`，零命中；`Agent$Action` 模型类里也没有 query 字段的读取（`dh0/s0.smali`、`cb0/g.smali` 搜 `getQuery`/`"query"` 零命中）。
3. **唯一像「来源判断」的东西与来源无关**：`dh0/b.smali isSilenceAction`（行1500起）判据是动作的 businessType 字符串含 `"obtain_form"` 或 `"fill_form"`（表单类静默执行）——判的是**动作类型**，不是**谁要求它**。
4. **caller tag 只记录不判断**：`AiActionProvider.doActionForSwitchAutoRotationMode`（settings_unpacked `smali_classes2/com/android/settings/provider/aiaction/AiActionProvider.smali:5363`）把 `"AiAction#doActionForSwitchAutoRotationMode"` 传给 `RotationPolicy.setRotationLock(Context, Z, String)`——这是 framework 的**日志来源参数**，本地代码中没有任何读取该 tag 做判断的路径。
5. **执行器侧唯一的身份校验是「调用者是不是 aicr」**（`smali_classes3/com/android/settings/utils/AiActionUtils.smali checkPermissions` 行956-1010：`Binder.getCallingUid()` → 包名必须 == `com.xiaomi.aicr`）——它防的是**别的 App 直接调执行器**，不区分 aicr 转发的动作里哪条有用户指令背书。

**「有实现/有生效」区分**：无相关实现可谈；`hp/a.q()`（smali/classes19/hp/a.smali:10545，"prePareActionQueue"）在执行前只做**格式校验**（Bundle 有效 / client_request_id 有效 / type 字段存在），逐行核对无来源字段参与任何分支。

## 二、Q2 幂等的边界

**结论：幂等只在执行层做「读当前值对比」，防重复写同一状态；不防来回横跳；指令链上无时间窗口、无按 URN 计数。**

1. **幂等在哪层**：执行层（执行器方法内），不是校验层。两处实现：
   - agent 链：`AiActionProvider.smali:5363` `doActionForSwitchAutoRotationMode`：`want = getSwitchStateFromJson(in)` → `current = RotationPolicy.isRotationLocked(ctx)` → `if (want == current) return`（不写）
   - 旧协议链：`cb0/u8.smali d0()`（行476起）：`getSettings(...)` 读当前值 → `if (new == old) { log "the value has not changed."; return }` → 才 `putSettings`
2. **判断依据是读系统当前值**，不是「记上次写了什么」——没有写入历史表（voiceassist 与 AICR 的执行链均无 history 持久化字段）。
3. **来回横跳绕过成立**：关→开→关→开，每一步 `want != current` 恒成立，幂等判断每次都放行。代码路径上没有任何额外条件参与（`doActionForSwitchAutoRotationMode` 的分支序列：解析→读值→对比→写，无其他检查）。
4. **时间窗口**：
   - 指令链：无。`hp/a` 与 AICR `d.smali` 的执行路径上无 elapsedRealtime/SystemClock 时间比较（`request_map` 是请求生命周期管理——`updateRequestStatus()`/`removeRequest()`（d.smali:13718/12942），无「同 key 拒绝」分支）
   - UI 卡片层：有，但不护指令。`xa0/b.smali:501 shouldDebounce()`（`elapsedRealtime - lastSwitchTime < interval` 即拒），调用者仅 `xa0/b` 自身与 `q90/y$b`（`SwitchPanelCard`，日志字符串 `"onCheckedChanged: debounced"`（q90/y$b.smali:100）直接写明是**卡片开关控件防重复点击**）。语音指令路径（`AgentActionOperation` → `dh0/s0` → AICR）不经过该控件。
   - `b6.getDebounceInterval`（classes9/b6.smali:3513）读 `Settings.System "content_observer_open_interval_time"`，同样只喂给 `xa0/b.setCardSwitchDebounceInterval`（卡片控件），有 `touch_assistant_enabled` 特判。
5. **按 URN 计数**：无。AICR `requestQueue = LinkedBlockingQueue(10)`（d.smali:444-457）是**并发排队容量**（在途上限 10），不是历史计数；`timeout_update_list`（d.smali:206）是单次超时管理。

## 四、Q4 用户可见性（上篇未查）

**结论：静默执行路径用户零可见；非静默路径的可见性 = 云端下发什么就显示什么，本地不生成成功回执；无产品级动作执行记录页；无撤销。**

1. **Toast**：设置类执行链五个文件全零——`cb0/u8`（SettingsWriteOperation）、`cb0/s8`（SettingsSwitchOperation）、`cb0/g`（AgentActionOperation）、`dh0/s0`、`dh0/l` 搜 `Toast` 均零命中；Settings App 的 `provider/aiaction/` 目录 Toast 零命中；AICR `hce_framework` 目录 Toast/NotificationManager 零命中。唯一例外 `cb0/ea`（SystemPowerOperation）的 Toast 是 `"mAdvertiseSettings == null"` 错误提示，与执行反馈无关。
2. **成功回执靠云端文案**：指令信封里有 `status_tts`/`action_status_tts` 字段（`rev/miui_VoiceAssistAndroidT/assets/action_data.json`——云端下发的播报文案列表）；`dh0/l.smali displayTts`（行916，日志 `"displayTts: text="`）只播 `extra_business_tts`（云端下发）。**本地执行成功时不生成任何播报**——旧协议链成功路径只有 `notifySwitchState(布尔)`（u8.smali N() 行295，通知 UI 卡片更新状态），失败路径才本地 TTS（`not_support_temporary`「暂不支持」）。
3. **卡片可见性 = 云端是否下发卡片模板**：`SystemControlCard`（classes7/.../instruction/card/SystemControlCard.smali，绑 `Template$ActionSwitchCard`）是开关卡片 UI；但静默动作（`isSilenceAction` → `dh0/l.execute`）走无卡片通道直接执行（dh0/s0.smali:1257-1270 silence 分支 postDelayed + 直接 `dh0/l.execute`）。**静默 = 无卡片、无 TTS 要求、无 Toast = 用户零感知**。
4. **执行记录页**：voiceassist 设置页全清单（res/xml/ 约 40 个 preference 页）无「执行记录」页；`privacy_management_settingss.xml` 全条目核对 = 权限开关管理（语音识别优化/日程获取/推送等），无动作审计；用户可见的记录只有**对话记录**（strings.xml `ai_more_record`「对话记录」、`chat_record_*` 系列）——聊天流卡片会留在对话里，但静默执行不产生卡片，即**不留痕**。
5. **撤销**：`undo/rollback/revert` 全库命中均为误报（AiImg2ImgActivity 图片编辑 undo、floatingtoolbar 资源、strings.xml `"memory_setting_forget_all_content"`「此操作无法撤销」记忆清空文案）。设置动作无撤销入口。
6. **厂商侧留存**：`ActionOneTrackHelper`（d.smali:738）= OneTrack 埋点上报——动作执行数据上报小米服务端，**用户在产品界面查不到**；caller tag 进框架日志（logcat 级，普通用户不碰）。

## 五、Q5 执行前确认

**结论：设置类动作无强制确认；确认卡片存在但由云端可选下发，设置类执行链与确认逻辑零关联。**

1. 确认机制存在：`ConfirmCancelBoxOperation`（classes7/cb0/d3.smali:88 getOpName "ConfirmCancelBoxOperation"）+ `ConfirmCancelBoxCard`——渲染确认/取消卡片。触发条件：云端下发对应 Template 指令（d3.smali:581 "onProcessOp, add ConfirmCancelBoxCard"——它是**渲染器**，是否弹确认由云端指令决定）。
2. 设置类执行链与确认的关联：`cb0/u8`、`cb0/s8`、`cb0/g`、`dh0/s0`、`dh0/l` 五个文件搜 `ConfirmCancelBox|confirm` **全零**——语音执行设置动作时无确认分支，`onProcessOp` 直通执行。
3. 执行器侧：Settings App `AiActionProvider.call`（smali_classes2/.../AiActionProvider.smali:8340起）流程 = `timeUpdated` → `checkPermissions`（调用者身份）→ method 分发 → **执行**，无用户确认环节。
4. 对照（危险动作也走跳转而非确认）：`jumpmasterclear`（恢复出厂设置入口，AiActionProvider doAction case 0）= 启动 `MiuiMasterClear` Activity——确认发生在**跳转后的设置页面**里，由该页面自己把关，不在动作执行链上。
5. `sysapps` 权限面补充核对：`com.xiaomi.aicr` 权限清单（100 条，sysapps.bayton.org）无确认类特殊权限；相关的是 `hyperos.permission.CALL_INSTRUCTION_ACTION`（进程间授权，非用户交互）。

## 八、我的疑问（标明推断）

1. 【推断】云端的对话管理（DM）层大概率有「同一意图的会话内去重」（同一轮对话不会重复执行同一动作）——这是任务编排的常识需求。但它最多只覆盖两类问题里的第一类，而且只覆盖单次会话：

   - **第一类：重复执行**（用户最烦的之一）——同一动作被反复触发。去重防的仅是单次会话内的重复，防不了跨轮次/跨会话。
   - **第二类：模型自主发起、动机不明的操作**（更难受的一类）——比如「方向锁定当前是 0，模型自己把它改成 1」。**这类操作单次就足够讨厌**，根本不需要重复；而且在对话层面看不出它为什么这么做，事后只能从行为倒推。

   **去重机制对第二类完全无效**——它不是重复，是首次。未证实，不进结论。
2. 【推断】埋点（OneTrack）上报的执行数据可能被小米用于云端异常检测——即使存在，也属事后分析，不是执行前的闸。未证实。
3. 【确认】所有 文件:行号 结论直接来自反编译产物，可复核；`grep 零命中` 的搜索命令与范围已在 §7 逐条写明。

## 踩坑记录区

1. **预判 2 应验且加码**：静默执行（silence）有独立执行器 `dh0/l`（ActionExecute）——不追这个类就会把「有卡片=TTS 播报」误当全部路径。它最终仍调 `hp/a.executeActionsAsync(JSONArray,...)`，**没绕过 check**，但**完全跳过 UI**。
2. **`isSilenceAction` 判据是 businessType 字符串（obtain_form/fill_form）**——名字里的 silence 是「不打断用户」的表单场景语义，不是「偷偷执行」开关；但效果上它定义了一条零可见执行通道。
3. **预判 4 应验**：`debounce` 是真命中（一阶段就撞见 `getDebounceInterval`），但它是 UI 卡片控件防抖（`SwitchPanelCard onCheckedChanged: debounced` 日志自证），差点被当指令链时间窗记入「有实现」。
4. **`request_map`/`timeout_update_list`/`requestQueue(10)` 三个字段名字都像频率管理**，实际是请求生命周期+超时兜底+并发排队——按字段名下结论会错。
5. **`cb0/yb`（extends instruction/base/b）的 getOpName 是动态拼接**，一阶段脚本标 "(no getOpName)" 的类需人工看——但本次与防乱用无关，未展开。
6. **res/values-zh-rCN/strings.xml 是最便宜的可见性证据源**：搜中文文案（「记录」「撤销」「确认」）比搜代码类名快且准——执行记录页、撤销文案的排除都靠它一击命中。
