## 摘要

1. **各自定位一句话**：豆馅=唯一开源的系统级集成样本，架构上最聪明的一步是把授权弹窗/敏感页阻断/handover 全部借给 Android 17 Computer Control 平台，自己只做编排；mobilerun=工程化最厚的编排框架（可抄的全是实战打磨过的小机制）；dsh-go=同类里安全闸密度最高的（AGPL，只抄思路）；MobileAgent=纯视觉路线的规模验证（手机侧从不读节点树）；Open-AutoGLM=demo 骨架（开源仓已停更，官方重心转封闭产品）。闭源侧：Google 把平台执行权在源码层钉死给「预装+助手角色」；豆包一代注入、二代改 SAEP 声明协议；三星唤醒靠场景分流模型通道；小米对第三方助手是主动守门而非被动枚举（ROM 双版解包实证，B 文件 §三）。
2. **最值得抄的三条**：① 豆馅 `TargetCheck.sameTarget`（执行前节点一致性，31 行纯函数）+ `ActionPolicy.assess`（58 行本地白名单）——直接补本项目 Guard 层；② dsh-go `PhoneTaskJournal` 中断记录 fail-closed（开工写「在跑」/重启见残记录拒开工待人 ACK）——补本项目 START_STICKY 自恢复后「不知道上次断在哪」的缺口；③ mobilerun 状态读取分级重试（超时只重试 1 次，DROID-305 教训）——本项目桥/设备 HTTP 层直接可用。
3. **最失望的一条**：Open-AutoGLM 的 README 与代码脱节——「黑屏自动检测并请求人工接管」在代码里不存在（`is_sensitive` 死标记，#384 实测接管回调不触发）；一个 26.6k★ 的官方仓库是论文配套 demo。
4. **一个坏消息**：「能走 API 的走 API」的最强形态 Google AppFunctions，其调用权在 AOSP 权限定义里就只给预装+ASSISTANT 角色——**本项目 sideload 形态结构性拿不到**；可行退路=deep link 优先 + 自家生态内做「应用声明边界」（豆包 SAEP/苹果 App Intents 的方向）。
5. **一个好消息**：本项目最难受的「微信控件树读不出」是全行业未解——字节（系统签名）都被 166 款 App 拒，MobileAgent 靠不读节点树绕开；P4 定级不是本项目做得差，是对手也没解。P1 唤醒同理：豆馅（同用 sherpa KWS）的调参注释原话承认没调出来，三星的生产答案是加场景模型通道而非调参。

## 二、逐组对照（九组）

> 本节主体为 A 档五仓 + AOSP；闭源厂商的对应结论在第六章与 B 文件，此处只在组尾给一行指针。

### 2.1 语音唤醒

#### 谁做了
- **豆馅**：全链路本地——sherpa-onnx KeywordSpotter（zipformer transducer，wenetspeech 3.3M），4 固定词（豆馅你好/你好豆馅/豆馅同志/同志你好，`android/tools/prepare_voice.py:89`）；AudioRecord + **隐藏 HOTWORD 音源 1999**（`LocalSpeechEngine.kt:185-186`）；息屏持续监听（PARTIAL_WAKE_LOCK，`VoiceService.kt:33`），命中但锁屏只提示解锁不执行（`VoiceRuntime.kt:186-188`）
- **mobilerun**：无（grep wake 全仓 0 命中——PC 侧形态，唤醒不适用；A4 笔记 5.1）
- **dsh-go**：无唤醒词（前置审计 H 节：「搜 wake/唤醒词/KWS 代码内未见」，只有听写）
- **A2 Open-AutoGLM**：无——且连 PC 侧「先亮屏再动手」都没做（grep wake/stayon/svc power 零匹配；PR #140 提案未合并，正文："the screen may enter sleep mode... causes subsequent actions to fail silently"）；**熄屏时截图得黑图、tap 空点，agent 会把 100 步烧完**（A2 笔记 5.1 + 疑问 2）
- **A3 MobileAgent**：无唤醒能力，全家族零处理（搜 keyevent 224/KEYCODE_WAKEUP 仅命中评测数据文件名）——**假设设备已亮屏解锁**，锁屏场景直接失效（A3 笔记 5.1）
- **闭源**：三星唤醒方案已逆向，是「按场景分流」思路且与本项目 P1/P2 直接相关（细节与证据只在 B 文件 §1.4，此处不留实现细节）；Google 平台容器 HotwordDetectionService（6.1.2）

#### 做了什么（豆馅关键机制）
- **状态栏麦克风指示处理**：`CAPTURE_AUDIO_HOTWORD`（privapp 白名单）+ HOTWORD 音源 → 系统计为 `RECORD_AUDIO_HOTWORD` AppOp，**SystemUI 的麦克风指示不计入它**（`os/custom/privapp-permissions-douxian.xml:6-7` 注释原文 "keeps the status bar's microphone indicator off"；机制长注释 `LocalSpeechEngine.kt:141-147`）。**功能性硬约束**：音频策略对 persistent 进程静音普通音源——「命令被静音」是当初反转的直接原因（见 3.1）
- **回退链**：打不开 HOTWORD 音源 → 回退 VOICE_RECOGNITION 并记事件（`LocalSpeechEngine.kt:148-152`）；无特权构建走普通音源
- **误唤醒**：调参留痕承认未达标（`LocalSpeechEngine.kt:217-218` ponytail 注释——72 合成样本 4 路径中 17、8 路径中 40、日常语音 10 分钟 0 命中、score 2.0 达 51 但会误触、阈值无效）→ 验收目标「8h 误唤醒 ≤2」仅在设计文档，未见实测达成

#### 可能是因为什么
见 3.1（HOTWORD 反转史，三源互证）。

#### 对我们意味着什么
- 豆馅与本项目同用 sherpa KWS，**它也没调好误唤醒**——「真人喊 5 次」实验仍是本项目 P1 的正确下一步，不是 KWS 换引擎
- 「播报期不被自己的声音唤醒」：豆馅=播报期暂停监听 + FGS 切 mediaPlayback；三星=播报场景独立模型通道（方向性结论，证据在 B 文件 §1.4）；**单机 App 级没人做真 AEC**（豆馅 git 搜 aec/echo 零命中）

### 2.2 保活

#### 谁做了
- **豆馅**（ROM 形态三重）：system 变体 `android:persistent="true"`（全仓唯一，`android/app/src/system/AndroidManifest.xml:7`）+ sysconfig `allow-in-power-save`（`os/custom/douxian.xml:4`）+ START_STICKY + 30 秒崩溃恢复测试（`os/custom/README.md:155-159` + `test_wake_recovery.py`）；**FGS 类型运行时切换** microphone↔mediaPlayback（`VoiceRuntime.kt:62,154,329`）
- **mobilerun**：不保活，被杀就恢复——Play Protect 静默杀 Portal 后 "Accessibility service not available" → **立即恢复**不等退避（`provider.py:42-44` + PR ee28316/#490）
- **dsh-go**（A5 补查）：DshService=`specialUse` FGS 类型（Manifest:250-257，带审核说明字段）；**电池豁免三级回落链**（`RuntimePlugin.kt:195-211`）+豁免状态进诊断；自恢复三层——引擎被杀 5/15/45s 三档限 3 次/10 分钟（`SafeMode.kt:35-39`）、连崩 2 次进安全模式、开机只恢复特权通道+无障碍（A11yKeeper 自动写回无障碍服务，带退避）；全 START_NOT_STICKY（靠主动监控不靠 sticky）；无 android:persistent（grep 零命中）；持**无超时** PARTIAL_WAKE_LOCK
- **A2**：无端侧进程，保活架构上不适用；但熄屏失效真实存在且未处理（同上）
- **A3**：无保活，靠固定 sleep 兜节奏（v3 首步 sleep(8) 防开屏弹窗 + 每步 sleep(2)，E 更是动作后 sleep 3-10 秒双保险）——**没有任何 stayon/wakelock 处理**，长会话设备自动锁屏无自愈
- **闭源**：三星保活底牌是系统件身份+常驻服务（逆向结论，B 文件 §1.5——普通 App 抄不了，细节不在此留）；Google 平台不给第三方留常驻位（HotwordDetectionService @hide，6.1.2）

#### 对我们意味着什么
「免常驻且唤醒词叫得起」在六个对象里**无先例**：豆馅用 ROM、三星用 DSP、mobilerun 用 PC 侧、dsh-go 用常驻引擎。本项目前台常驻形态维持，省电优化走豆馅 FGS 切换 + 电池白名单引导（ROADMAP 补法清单②不变）。

### 2.3 权限模型

#### 谁做了
- **豆馅**（分层最清晰，详见 A1 笔记 5.3）：
  - privapp 白名单**只有 3 项**（WRITE_SECURE_SETTINGS / ACCESS_COMPUTER_CONTROL / CAPTURE_AUDIO_HOTWORD），每项带注释；`test_image.py` 强制白名单与 Manifest 双边一致（缺项不开机）
  - **INJECT_EVENTS 全仓零命中**（grep 复核 0）——豆包被报道的系统签名注入，在这个开源 OS 里**没有对应物**；跨应用靠无障碍 dispatchGesture 与 Computer Control
  - 本地确定性拦截：密码页暂停+拒截图+节点文本置空（`TaskController.kt:477-480`、`AndroidPhone.kt:95,337,343-346`）；聊天框回车不发消息（`ActionPolicy.kt:13-27`）；手势越界拒绝+截图区域比对（`ActionPolicy.kt:45-46`、`AndroidPhone.kt:239-252`）
  - 模型层 handover 审批链（凭据/付款/删除/账号安全必须 handover，审批只覆盖具名动作且进 Evidence）
- **mobilerun**：无权限闸（编排层没有跨应用审批）；敏感处理=type_secret 全链路掩码（`actions.py:627` + PR #534：typed 值注册 per-run redactor，UI 树/日志/宏/trace 统一 `[secret:<id>]`）
- **dsh-go**：前置审计 C 节已覆盖（原生 SafetyGate + 29 金融包 deny + 解除限制 1.5s 按住 + 确认卡拒注入触摸）
- **A2**：无端侧组件——权限=用户手工前置配置（USB 调试+(安全设置)+外装 AdbKeyboard IME）；支付页 FLAG_SECURE 截图失败被当黑图处理
- **A3**：同 PC 端路线——设备侧持久改动=装 ADBKeyBoard.apk+改默认输入法（v3.5 部署 9 步注释写死，**小米 HyperOS 要另开「USB 调试（安全设置）」**，`utils.py:41`）；运行时权限弹窗纯 prompt 约束「关掉、永不登录」+ E 的 tips 支付红线「Do not add any payment information」
- **闭源**：三星特权靠系统件身份与平台签名（逆向细节在 B 文件 §1.3，此处不展开）；Google AppFunctions 三层校验（6.1.1）；豆包一代 INJECT_EVENTS→二代 SAEP（6.4）

#### 对照本项目
`docs/权限.md` §5 的「48 工具零闸」是 **2026-11-05 Guard 上线前的旧结论**（A5.5 验收后：原生 dex Guard + confirm flavor 真机验收「日常操作零弹窗/支付宝读屏拒绝」）。对照后真实差异：本项目 Guard 判定层与豆馅 ActionPolicy 同深度，**缺的是**：①豆馅的「执行前节点一致性校验」（sameTarget）②豆馅的审批进 Evidence ③dsh-go 的金融包出厂 deny 名单。

### 2.6 界面理解

## 三、动机分析（专章，按三段式）

### 3.1 豆馅：用 CAPTURE_AUDIO_HOTWORD 让麦克风指示灯不亮（含反转史）

**做了什么**：唤醒监听与助手指令录音都走隐藏 HOTWORD 音源（1999）+ privapp 授 CAPTURE_AUDIO_HOTWORD；SystemUI 麦克风指示不计入 RECORD_AUDIO_HOTWORD AppOp。证据：三处①级注释（`privapp-permissions-douxian.xml:6`、`system/AndroidManifest.xml:6`、`LocalSpeechEngine.kt:141-147`）+ `acceptance.md` v1.29 真机 dumpsys 取证（不出声时 RECORD_AUDIO_HOTWORD 持续运行、RECORD_AUDIO 无记录、PrivacyItemController 为空、状态栏截图无指示点）。

**可能是因为什么（证据等级①+③）**：
- 隐私动因（① `acceptance.md:369`）：「机主反馈不触发唤醒词时状态栏右上角也一直有绿色指示点」
- 功能性硬约束（① `LocalSpeechEngine.kt:143-146` 原文）：音频策略把无障碍服务排除在 "top or latest" capture 之外，persistent 进程以普通音源录音「every command was silenced」——**不换音源就没有功能**
- 反转史：设计文档 2026-10-09 原计划「不引入 CAPTURE_AUDIO_HOTWORD 或 HotwordDetectionService」（隐私保守取向），3 天后 commit `c5f90da`（2026-10-12 "listen for the wake word as a hotword client so the microphone indicator stays off until a command"）+ `24f7f5c`（指令录音也走 HOTWORD）反转

**交叉验证**：①注释 ×①验收记录 ×③commit 三方一致 + 真机 dumpsys/截图；README 与代码注释在「指令录音亮不亮灯」上有一处矛盾（README:64 说指令时亮，代码注释+commit 说也不亮——以代码+commit 为准，README 已过时；两处都列出，不抹平）。
**评价**：技术手法可学，「让系统隐私指示不亮」这个效果对外发产品是负资产——豆馅是自刷自用语境的知情选择。

### 3.2 豆馅：persistent 系统应用 +「任务不重放」成对设计

**做了什么**：persistent=true（system 变体）+ allow-in-power-save + 自恢复无障碍开关；但任务从不在进程死亡后重放——重连统一改判 INTERRUPTED。
**可能是因为什么（①）**：设计文档原文「进程异常退出后由系统恢复，但不会自动重放未完成任务」；代码注释「Tasks never outlive the service, including those waiting for manual intervention」（`AssistantService.kt:217`）。
**交叉验证**：acceptance.md 每个 v1.x 重复检查「系统持久标记」；①③一致，动机清楚（常驻为唤醒、不重放为安全，边界自觉）。

### 3.3 豆馅：跨应用选 Computer Control 虚拟屏而不是无障碍直接操纵

**做了什么**：OS 内任务默认跑 Android 17 Computer Control 会话；授权/阻断/handover 都落在系统能力上（逐应用系统弹窗、SECURE/认证页系统级阻断、allowlist provider），自有代码只做编排。
**可能是因为什么（①）**：`VirtualPhone.kt:76-77`「so the phone stays free while a task runs」（用户手机不被占用是第一动机）；`AllowlistProvider.kt`「the app scope and the system's per-app consent still limit what runs」（治理借用系统）。
**交叉验证**：os/README「虚拟屏执行」整节 + RRO 配置 + test_image.py 一致性校验；①级充分。**这是九组问题里架构上最聪明的一步**——把确认弹窗、敏感页阻断、前台/后台隔离全部借给平台。

### 3.4 豆馅：Jev 小模型先行 + 视觉并行兜底

**做了什么**：每步先让便宜模型选动作；视觉调用同时起跑，Jev 拿不准/失败才用；Jev 确定则取消视觉。
**可能是因为什么（①）**：`TaskController.kt:292-295` 原文写明代价自白「at the price of a vision request on steps Jev could do alone」；placement 注释「A slow Jev is not worth waiting another model for: on 2026-10-15 that cost 13.6 s」。
**交叉验证**：①×③（README「先读元素，再看画面」）一致，动机=延迟。

### 3.5 mobilerun：超时读状态只重试一次

**做了什么**：普通错误 7 次退避（1+2+3+5+8+10≈29s）；超时只重试 1 次（`provider.py:49` `_MAX_TIMEOUT_ATTEMPTS = 2`）；a11y 服务报错立即恢复；3s 未响应打 INFO 防误判挂死。
**可能是因为什么（②+①）**：commit 2d13908 原文：设备端串行处理请求，「the old 7-attempt schedule queued six more reads behind a stuck app: up to ~4 minutes of `device ui --ios` with nothing printed for the first 30s (DROID-305, mobilerun#484)」；gh issue #484 存在（closed）；专项测试 test_state_fetch_retry_policy.py 锁行为。
**交叉验证**：②issue ×③commit ×①注释 ×测试，证据充分。

### 3.6 mobilerun：按模型声明「坐标契约」

**做了什么**：给模型的坐标空间必须等于模型实际看到的图的空间——vision_sizing.py 按 provider 精确换算（Anthropic 1568/2576，Gemma 归一化）。
**可能是因为什么（②）**：gh #365 "Anthropic vision downsizing causes coordinate actions to land short"（closed）+ commit 6ceb40a + 5 个相关 commit + 3 个测试/评估脚本。
**交叉验证**：issue+commit+测试完整，是 mobilerun 打磨最认真的一块。

### 3.7 Open-AutoGLM：action 解析从 eval 换成 ast

**做了什么**：`phone_agent/actions/handler.py:355-372` 用 `ast.parse` + `ast.literal_eval` 解析模型输出的 `do(...)` 调用；:355 注释原文 "Use AST parsing instead of eval for safety"。
**可能是因为什么（①）**：防模型输出/注入的表达式被当 Python 执行——模型输出直接进解释器是这个架构的原生风险面。
**交叉验证**：①注释 ×③commit 8c10bf7 "replace eval with ast" ×②PR #152 分支名 `update-eval-security` 三源一致。残留问题也如实记：解析前仍做 `response.replace('\n','\\n')` 字符串补丁——模型输出格式脆弱、靠点状补丁续命。

### 3.8 dsh-go：定时任务的独立授权闸（不用 approval/request）

**做了什么**：模型创建或修改定时任务必须过一道**独立**的 userQuestions 授权（120s 超时、确认卡展示完整任务 JSON、逐字段精确匹配「授权」二字、子代理一律拒、过期时间拒、写回竞态检测）。
**可能是因为什么（①级补丁注释原文）**：`zzzzzzzz-schedule-authorization.diff:163-164`——"Questions have no auto-approve path, including on older clients. Do not use approval/request: full-access sessions and allow-all clients bypass that gate."——**因为完全权限会话和「总是允许」客户端会绕过 approval 闸**，所以换成没有任何自动批准路径的机制。
**交叉验证**：①补丁注释 ×①用户文档（`docs/guide/zh/01-chat.md:72-74`「完全权限、自动审查和本对话自动允许都不能代替这次确认」）一致；逐条核对 diff（4 条拒绝路径+子代理拒绝+过期拒绝+竞态检测）。
**对照本项目**：A7 AlarmKick 方案里「定时任务本身要人工授权」这条边界，dsh-go 已经把踩坑后的完整答案写好了（尤其「子代理拒绝」与「过期时间拒绝」是我们想不到的两条）。

### 3.9 MobileAgent：从「外挂感知全家桶」到「模型内建 grounding」（v2→v3）

**做了什么**：v1/v2 要在 PC 端跑 OCR+GroundingDINO+CLIP+Qwen-VL caption 四个外挂模型才能把屏幕变成坐标列表；v3 把这些全删了，坐标由 GUI-Owl 直接输出，PC 端只剩 adb 封装。
**可能是因为什么（②+①+④）**：issue #180（全仓最高评论数 21 条）用户实测总结原文：「之前使用mobileAgent2测试,当时有感知模块...会感知每个元素的坐标,准确率比较高...但 VL 模型不擅长定位精确坐标...适合让操作 agent 直接在屏幕元素列表...选中一个元素执行操作」——坐标错位是 v2/v3 时代用户头号痛点（#180/#182/#207 全是坐标问题）；①README 对 GUI-Owl「perception, grounding, and end-to-end operation」的定位描述；④评测榜上 native GUI model 数据更好看的商业动机（推断）。
**交叉验证**：②issue 多人实测 ×①README ×③论文（v3 arXiv 2508.15144）方向一致；但「删感知链」的完整动机只有④级推断，标「部分清楚」。

### 6.1 Google（三层分写）

#### 6.1.1 平台权限层（AOSP 源码，可信度高）

**AppFunctions 调用方校验三链**（`CallerValidatorImpl.java`，googlesource main @ 1cdfff555，本地 `G:\code\ai-phone-audit\aosp\`）：
1. 自称包名必须与 binder UID 吻合（L243-256）
2. 执行他人函数三选一（L93-146）：自己包 / `EXECUTE_APP_FUNCTIONS_TRUSTED` / `EXECUTE_APP_FUNCTIONS`+目标未设 restrict

**两条关键权限（`core/res/AndroidManifest.xml`）**：
- `EXECUTE_APP_FUNCTIONS_TRUSTED`（L8301-8308）：只给 SYSTEM_UI_INTELLIGENCE 角色（CDD 9.8.6 Content Capture），**应用无法 opt-out**

**生效版本**：Android 16+（`@FlaggedApi` 门控；官方文档原文）。
**对照 GuardImpl**：官方校验=身份（UID）+ 角色（授予面）+ 目标方 opt-out 三层；本项目 Guard=通道分级+动作分类+前台包名 fail-closed——官方的「目标方 opt-out」是本项目没有的一层（应用自己可以说「不许 Agent 调我」）。

### 6.2 小米澎湃 OS——国行 vs 外版对照

#### 6.2.1 两版 AI 包的差异清单（ROM 实解，证据在 B 文件 §3.2）

解包实证（国行 `OS3.0.307.0.WNCCNXM` vs 全球 `OS3.0.305.0.WNCMIXM`，小米 14 / HyperOS 3 / Android 16）——细节与证据文件在 **B 文件 §3.2**，此处只留方向性结论：

1. **全球版给 Google 助手栈 priv-app 预装待遇**（搜索 App、应用商店、唤醒注册包、设备智能服务等全套进特权位，包名清单见 B 文件 §3.2）；国行只有 GMS 底座（无搜索 App/Play 商店）
2. **国行小爱是三层结构**：桌面 AI 助理 priv-app → 语音助手 app 层（`com.miui.voiceassist`——包名经 gemini-mi 公开源码亦可证，VIS 注册者）→ 语音引擎 data-app 层（microphone 前台服务）——特权递减
3. **小米 AI 底座两版同包同尺寸**——跨版本共用
4. **唤醒的 DSP 层两版逐字节相同**（高通供应商件+声学模型，细节见 B 文件 §3.4），「谁被唤醒」由 AP 侧谁向 SoundTrigger 注册决定
5. **两版 privapp-permissions 的 hotword/soundtrigger 授予面几乎一致**——「系统方怎么约束外来 AI」的答案不在权限面，在**包的存在性与助手角色归属**（见 6.2.2 模块侧机制）

#### 6.2.2 系统方对外来 AI 的约束逻辑 ⭐（模块侧，公开 GitHub 源码 → 归本文件）

三个模块仓库给出「国行怎么约束外来 AI」的三层机制（**间接证据**：hook 目标反推系统行为；与 ROM 解包互证后可升级）：

1. **系统层守门**（gemini-mi `AssistantPersistHook.java:53-56` 注释原文）：「MIUI 在开机后会主动把 voice_interaction_service / assistant 写回小爱」——模块必须 hook `Settings.Secure.putStringForUser` 拦截；写这些键需要 system 身份（`:139-166`，system_server startOtherServices 后写 + USER_UNLOCKED 再写）
2. **归零逻辑**（`AssistantPersistHook.java:26-27`）：界面显示成「未选择」会「导致 MIUI 内部的归零逻辑触发」——MIUI 不是被动枚举，是主动守门；**一加可见/小米不可见与此同方向**（一加近原生枚举，MIUI 有自己的判定层）
3. **小爱层抢回**（`XiaoAiPowerKeyDisableHook.java:10-13`）：小爱 `power_wakeup` preference 开机重新置位电源键唤醒——模块 hook SharedPreferencesImpl 读写强制 false
4. **Google 自身区域闸**（`SimSpoofHook.java`）：TelephonyManager/SubscriptionInfo/SystemProperties 全家伪装美区 SIM；**Google App 把服务端检测的国家存 SharedPreferences key "cy"，能覆盖本地 API**（`:128-131`）——区域判定有服务端成分
5. HyperOS 4（Android 15+）电源键路径换到 system_server 侧（fulu2778 `HookEntry.java:33-47` API102），圈定即搜还要在 Google 进程伪装设备支持

**对「系统方怎么写约束作业」的回答**：三层=①设置键的主动回写（开机）②UI「未选择」态触发归零 ③自家助手对触发入口（电源键/小白条）的抢占。**这套约束对任何第三方助手一体适用**——本项目 P1 挂点大概率不是「三件套写错」而是「MIUI 的守门层根本不给非商店/非白名单 App 进枚举」。
