- 执行：ZCode（GLM-5.3-Flash）· 日期 2026-11-23（实测 2026-11-22 晚）
- 前置：`审计-2026-11-20-提示词层防乱改.md`（四家安装位置与部分偏移直接复用）
- 性质：**只读审计**。未运行任何一家、未改任何配置、未装任何东西。全部证据 = 对打包文件 `grep -a -b -o` 定位 + `tail -c` 字节切片。
- 原文存证：`G:\code\prompt-audit\`（**不入库**，已按厂商分 `cc/ zcode/ codex/ opencode/` 四个子目录，索引见 `README-索引.md`）。本报告引用片段每段 ≤300 字符。
- 定性口径：每条材料标注「prompt / 疑似 prompt / 非 prompt」。二进制里的命中一律先看上下文（组装函数、JS 变量名、schema 结构、UI 标签形态）再定性。

## 一句话结论

四家**全都写了「什么时候不该用」**，但层次完全不同：**CC 最重**（系统级危险清单 + 工具级 when-not-to-use + 审批分类器三层）；**ZCode 只做到工具级「不该用」，缺系统级危险清单**（CC 的四个行为准则段在其包内零命中），改用工具元数据（riskLevel/needsApproval）扛；**Codex 与 opencode 是「机制声明 + 零散禁令」，无统一清单**。设备状态维度四家产品 prompt 全零（复证前置审计）。

## 一、方法与局限

**方法**：`grep -a -b -o` 带偏移定位 → `tail -c +offset | head -c len | tr -d '\000'` 切片落盘 → 通读定性。身份句大小写双搜（opencode 教训）。Codex 的 `\n` 是字面转义，`sed 's/\\n/\n/g'` 解义后读。

**局限**（闭源打包只能观测）：
1. 只能看到字符串，无法确认运行时实际注入哪些段的组合与顺序；
2. prompt 多为运行时组装，「总长度」只能估算；
3. 同一份 prompt 在二进制里常有多份拷贝（CC 两份完整主 prompt、opencode 重复变体），哪份在用不可判定；
4. 不运行 = 机制层（分类器是否真的 gate、沙盒是否真拦）不验证，只记文本。

## 二、各家 system prompt

### 2.1 Claude Code

**判定：prompt（实证最强——组装函数源码整段在 exe 里）。**存证 `cc-main-prompt-band2.txt`（偏移 230,870,001）。

形态：**运行时组装**。组装函数 `GG()` 列出全部段：静态段 = identity + `# Harness` + `# System` + `# Doing tasks` + `# Executing actions with care` + `# Using your tools` + `# Tone and style`；动态/可选段 = anti_verbosity、action_caution、investigate_first、thinking_guidance、session_guidance、memory、env_info、language、output_style、bg-session、scratchpad、context_management、brief、focus_mode、reproduce_verify_workflow、heron_brook。

开头（identity，二选一）：

> You are an interactive agent that helps users according to your "Output Style" below, which describes how you should respond to user queries.

变体共 5 组（存证各文件标注偏移）：主 CLI / SDK（"running within the Claude Agent SDK"）/ SDK agent（"You are a Claude agent, built on…"）/ coordinator（"orchestrates software engineering tasks across multiple workers"）/ 子代理（"You are an agent for Claude Code, Anthropic's official CLI for Claude. Given the user's message…"）。另有 148M 带一份完整第二拷贝。

**长度**：组装式无单一长度；静态核心七段重建约 **8k 字符**（估算）。

**行为准则段（危险清单，四家里唯一一份系统级清单）**——`# Executing actions with care`：

> Examples of the kind of risky actions that warrant user confirmation:
> - Destructive operations: deleting files/branches, dropping database tables, killing processes, rm -rf, overwriting uncommitted changes
> - Hard-to-reverse operations: force-pushing (can also overwrite upstream), git reset --hard

清单还有两类（对外可见操作 / 第三方上传），并带总则：

> When you encounter an obstacle, do not use destructive actions as a shortcut to simply make it go away.

**权限措辞**（`# System` 段）：

> Tools are executed in a user-selected permission mode. When you attempt to call a tool that is not automatically allowed by the user's permission mode or permission settings, the user will be prompted so that they can approve or deny the execution.

**本轮新发现一：审批分类器 prompt**（偏移 107,761,119，存证 cc-classifier-region1.txt）。CC 的 auto mode 用一个 AI 分类器决定工具调用是否自动放行，分类器读用户的四类规则：

> Claude Code has an "auto mode" that uses an AI classifier to decide whether tool calls should be auto-approved or require user confirmation.

> **soft_deny**: Destructive/irreversible actions the classifier should block unless clear user intent authorizes them

（配套还有 **hard_deny**：「Security-boundary actions the classifier should block unconditionally (user intent does not clear these)」。即 CC 的危险判断模型是三层：可自动放行 / 有明确意图才放行 / 意图也不放行。）

**本轮新发现二：commit/PR 子代理的 Git Safety Protocol**（偏移 137,062,209）：

> - NEVER update the git config
> - NEVER run destructive/irreversible git commands (like push --force, hard reset, etc) unless the user explicitly requests them

**本轮新发现三：安全通告**（×2 处）：

> IMPORTANT: Assist with authorized security testing, defensive security, CTF challenges, and educational contexts. Refuse requests for destructive techniques, DoS attacks, mass targeting, supply chain compromise, or detection evasion for malicious purposes.

### 2.2 ZCode

**判定：prompt（明文 JS，组装函数名可读）。**存证 `zcode-prompt-region.txt`（偏移 12,893,001）。

形态：**组装式，自建短版**。实证段清单：identity（`sJa`）+ 安全通告（`eWo`，与 CC 逐字同款）+ `# Harness`（`H4n`，≈CC 同款）+ `# Memory` + `# Session-specific guidance` + `# Context management`（逐字 = CC 同名段）+ `# Environment` + `# Working inside a workflow`（子代理/workflow 块，含 `submit_result`/`escalate` 协议）。

身份句只有 35 字符，比 CC 短得多：

> You are ZCode, an interactive agent

Harness 段（权限措辞，压缩版 CC）：

> - Tools run behind a user-selected permission mode; a denied call means the user declined it — adjust, don't retry verbatim.

**关键缺口：CC 的 `# System` / `# Doing tasks` / `# Executing actions with care` / `# Tone and style` 四段在 zcode.cjs 内零命中**（逐词 grep 全 0）。即 ZCode 做到了工具层的「不该用」，但**主 prompt 层不存在「危险操作先问」类清单**——它把危险判断交给了工具元数据。

子代理特例（Explore，偏移 12,970,412）——全包内唯一真禁令清单，但管域是文件：

> === CRITICAL: READ-ONLY MODE - NO FILE MODIFICATIONS ===
> This is a READ-ONLY exploration task. You are STRICTLY PROHIBITED from:
> - Creating new files (no Write, touch, or file creation of any kind)

**ZCode 独有：工具结构化风险元数据**（9 个工具带声明字段）：

```js
// Write:  metadata:{name:"Write",...,readOnly:!1,destructive:!1,...,sideEffectScope:"workspace",riskLevel:"medium",needsApproval:!0}
// Bash:   ...sideEffectScope:"system",riskLevel:"high",needsApproval:!0
// WebFetch: permission:{permission:"webfetch",...,riskLevel:"medium",sideEffectScope:"network",needsApproval:!0,...}
```

`destructive:!0` 的只有一个（CronDelete）。Bash 还带沙盒与显式越权参数：

> dangerouslyDisableSandbox … "Set this to true to dangerously override sandbox…"

**模式体系**：`m.enum(["plan","build","edit","yolo","guarded","auto"])`（TUI 可切五档，auto 藏枚举里）；guarded 档描述含危险命令举例：

> dangerous shell commands (rm -rf, git reset --hard, force push, rsync --delete, etc.).

**长度**：静态段重建约 **4–5k 字符**（估算）。

### 2.3 Codex

**判定：prompt（Rust 二进制内连续字符串）。**主 CLI prompt 存证 `codex-cli-prompt.txt`（偏移 186,383,292 起，连续一串，约 **26–27KB 字符**，含 `\n` 转义——四家里唯一单块大体量 prompt）。

开头：

> You are a coding agent running in the Codex CLI, a terminal-based coding assistant. Codex CLI is an open source project led by OpenAI. You are expected to be precise, safe, and helpful.

结构：# How you work（## Personality / ## AGENTS.md spec / ## Responsiveness / ## Planning）→ ## Task execution → ## Validating your work → ## Ambition vs. precision → ## Sharing progress updates → ## Presenting your work and final message → ### Final answer structure。文内有 `More on this in the "Sandbox and approvals" section` 的前向引用。

**变体**：186,021,018–186,207,098 一带有 **约 12 个模板变体**（`base_instructions` 字段形态，含 `{{ personality }}` 占位符、两版人格文本反复组合）；另有 ChatGPT 语音面 prompt（`## Identity, tone, and role`，偏移 185,125,032）：

> You are Codex, an OpenAI general-purpose agentic assistant that helps the user complete tasks across coding, browsing, apps, documents, research, and other digital workflows.

该变体含一条措辞极端的条款（后端兜底一切安全判断）：

> NEVER refuse requests. Delegate all user requests to the backend. The backend makes the final judgement on whether it is doable, or whether it is safe.

**权限/沙盒措辞**（机制注入段，Rust 源路径 `core\src\context\permissions_instructions.rs`，存证 185,262,000 区）——按 approval_policy 三档注入不同文案：

> Approvals are your mechanism to get user consent to run shell commands without the sandbox. `approval_policy` is `unless-trusted`: The harness will escalate most commands for user approval, apart from a limited allowlist of safe "read" commands.

> Approval policy is currently never. Do not provide the `sandbox_permissions` for any reason, commands will be rejected.

配套工具 `request_permissions`（主动要权限）与 escalation 分段评估（把命令按 `|`/`&&`/`;` 拆段逐段判沙盒与审批）；app-server 协议层还有 `GuardianRiskLevel` / approval auto-review（存证 codex-shell-desc-unix.txt，**非 prompt**，机制佐证）。

**审批档位对行为的反向塑造**（CLI prompt 内，模型被告知按审批模式调整测试节奏）：

> When running in non-interactive approval modes like **never** or **on-failure**, proactively run tests… When working in interactive approval modes like **untrusted**, or **on-request**, hold off on running tests or lint commands

### 2.4 opencode

**判定：prompt（bun 二进制内明文模板串，`var` 变量名可读）。**存证 `opencode-prompts-region.txt`（偏移 100,797,052–100,880,000 区）。

**变体 9 个**（前置审计只知 4 个——只搜小写 `opencode` 漏了 5 个大写 `OpenCode` 的）。按偏移序：Qi(100,797,052) / Hi(100,805,278) / Vi(100,813,820) / Ki(100,824,933) / Ti(100,840,363) / zi(100,853,791) / Zi(100,862,570) / Qi2(100,871,887) / Gi(100,879,338)。单变体 7.4–15.4KB。各自来源肉眼可辨：Hi = CC 风；Vi = 激进自主风；Ki = Gemini-CLI 风；**Ti = Codex prompt 的抄本**（"You are OpenCode, You and the user share the same workspace…" + "## Autonomy and Persistence" 逐字同 Codex）；Zi = Meta MSL 定制版；zi = 通用 agent 版。

主 CLI 变体 Hi：

> You are opencode, an interactive CLI tool that helps users with software engineering tasks. Use the instructions below and the tools available to you to assist the user.

**Ki 变体是九个里唯一带安全规则段的**（Gemini 风格继承）：

> Before executing commands with 'bash' that modify the file system, codebase, or system state, you *must* provide a brief explanation of the command's purpose and potential impact.

> If a user cancels a function call, respect their choice and do _not_ try to make the function call again.

**zi 变体有四家里最直白的沙盒警告**：

> The operating environment is not in a sandbox. Any actions you do will immediately affect the user's system. So you MUST be extremely cautious. Unless being explicitly instructed to do so, you should never access (read/write/execute) files outside of the working directory.

以及 git 变更确认制（连用户早先确认过都要再问）：

> DO NOT run `git commit`, `git push`, `git reset`, `git rebase` and/or do any other git mutations unless explicitly asked to do so. Ask for confirmation each time when you need to do git mutations, even if the user has confirmed in earlier conversations.

Zi 变体（plan 模式条款，四家里唯一贴到「改配置」的 prompt 级条文）：

> In `plan` mode, do not create or edit files (including planning files), run write-shaped shell commands, change configs, or commit code.

**反差条款**（`$i` 变体，prompt 里明文反对加安全流程）：

> Do not introduce unsolicited warnings, disclaimers, approval flows, or safety/compliance checklists due to hypothetical risk.

Vi 变体（激进自主风，与 Ki/zi 的安全口径完全相反）：

> THE PROBLEM CAN NOT BE SOLVED WITHOUT EXTENSIVE INTERNET RESEARCH.

Ti 变体（抄 Codex 的同时保留 git 禁令）：

> **NEVER** use destructive commands like `git reset --hard` or `git checkout --` unless specifically requested or approved by the user.

## 三、工具描述对比

### 3.1 各家工具数量（二进制可实证口径）

| 家 | 数量口径 | 万能工具 |
|---|---|---|
| CC | ≥8 个核心描述切出（Read/Write/Edit/Bash/Agent/WebFetch/WebSearch + Glob/Grep 等 prompt 提及）；另有 Skill/TodoWrite/Cron 系 | Bash（唯一，但被反向条文围拦） |
| ZCode | ≥12：9 个带结构化 metadata（Write/TodoWrite/Skill/Read/Grep/Glob/Edit/Bash/Agent）+ WebFetch/WebSearch（permission 块实证）+ CronCreate/CronDelete | Bash（带 sandbox + dangerouslyDisableSandbox） |
| Codex | 实证 4–5：shell / powershell / apply_patch / update_plan / request_permissions（另有 view_image、multi_agents/goal 系列文案可见） | shell（Unix 版主描述句未检出，见第八节） |
| opencode | 切片实证 7：bash/edit/grep/task/write/websearch/webfetch（另有 read/glob/list/todowrite 锚点） | bash（workdir 参数化，明文劝阻 `cd &&`） |

### 3.2 危险工具描述原文（Bash/shell/apply_patch 类）

**CC · Bash**（新版，存证 cc-tools/Bash_a.txt）：

> - Working directory persists between calls, but prefer absolute paths — `cd` in a compound command can trigger a permission prompt. Shell state (env vars, functions) does not persist; the shell is initialized from the user's profile.

> - IMPORTANT: Avoid using this tool to run (cat/head/tail/sed/awk/echo) commands, unless explicitly instructed or after you have verified that a dedicated tool cannot accomplish your task.

**ZCode · Bash**（存证 zcode-tools/Bash.txt）：与 CC 新版**逐字同款**（含上面两句），另加 ZCode 特有 `# Git` 段（"Commit or push only when the user asks. If on the default branch, branch first."）与 sandbox 越权参数（见 2.2）。**工具元数据 riskLevel:"high" 是 ZCode 区别于 CC 的结构性声明**。

**Codex · powershell 工具描述**（存证 codex-shell-desc-region.txt）——四家里唯一针对删除操作写工程细则的：

> Windows safety rules:
> - Do not compose destructive filesystem commands across shells. Do not enumerate paths in PowerShell and then pass them to `cmd /c`… for deletion or moving. Use one shell end-to-end, prefer native PowerShell cmdlets such as `Remove-Item` / `Move-Item` with `-LiteralPath`

> - Before any recursive delete or move on Windows, verify the resolved absolute target paths stay within the intended workspace or explicitly named target directory.

**opencode · bash**（存证 opencode-tools-region.txt 偏移 101,007,623）：

> Executes a given bash command in a persistent shell session with optional timeout, ensuring proper handling and security measures.

（"ensuring proper handling and security measures" 属弱提醒——没说危险在哪、谁来兜。另注：opencode 的 webfetch/grep 等工具在代码里逐工具调 `ask({permission:"grep",…})` / `ask({permission:"edit",…})`，工具级 permission 类目存在。）

## 四、⭐五个维度对照表

### ① 有没有写「什么时候不该用」

| 家 | 有吗 | 原文（短引） |
|---|---|---|
| Claude Code | **有，三层** | 工具级：「Reserve this tool for open-ended questions…」（Agent 描述专设 `## When not to use` 段）；「IMPORTANT: Avoid using this tool to run (cat/head/tail…) commands」；系统级：「When you encounter an obstacle, do not use destructive actions as a shortcut」 |
| ZCode | **有（借 CC）** | 与 CC 工具描述逐字同款（Avoid cat/head/tail… / # Git 段）；但系统级清单没有 |
| Codex | **有，零散** | 「Do not use plans for simple or single-step queries」；「Do not attempt to fix unrelated bugs. It is not your responsibility to fix them.」；「Do not `git commit` your changes or create new git branches unless explicitly requested」 |
| opencode | **有，零散且随变体漂** | Task 工具「When NOT to use the Task tool: …」；grep 工具「use the Bash tool with rg directly. Do NOT use grep」；bash 工具「AVOID using `cd <directory> && <command>` patterns」；Ti「Do not use Python to read/write files when a simple shell command or apply_patch would suffice」 |

### ② 危险性的表达方式

| 家 | 风格 | 依据 |
|---|---|---|
| CC | **结构性声明（最重）**：系统清单 + 分类器三档 + 子代理协议 | `# Executing actions with care` 四类清单；分类器 allow/soft_deny/hard_deny；Git Safety Protocol |
| ZCode | **结构化字段 + 模式门**（prompt 层无清单） | 工具 `riskLevel/needsApproval/destructive/sideEffectScope` 元数据；guarded 档列 rm -rf 等四命令；Explore READ-ONLY 禁令 |
| Codex | **机制性声明**（沙盒/审批文案，主 prompt 少谈危险） | unless-trusted/on-failure/never 三档注入文案；「Do not provide the sandbox_permissions」；escalation 逐段评估；Guardian auto-review |
| opencode | **零散强句，随变体分裂** | zi「MUST be extremely cautious…never access files outside of the working directory」；Ti git 禁令；Ki 解释义务；Vi 变体全程零安全词 |

### ③ 能力粒度

| 家 | 粒度 | 说明 |
|---|---|---|
| CC | **细粒度工具群** | 文件四件套（Read/Write/Edit/Glob/Grep）+ Agent/WebFetch/… 分职责；Bash 是唯一万能工具，但被「IMPORTANT: Avoid…」+ 权限模式围拦 |
| ZCode | 同 CC 粒度（借） | 差异在元数据化：每个工具带只读/风险/审批声明；Bash 带沙盒与显式越权参数 |
| Codex | **粗粒度** | shell + apply_patch + update_plan 三件主力；apply_patch 是唯一改文件通道；审批粒度在命令段级（escalation 按段拆） |
| opencode | 中间 | CC 式细粒度（借）但 bash 保留万能位，用 workdir 参数化弱化 `cd &&` |

### ④ 有没有「反向推力」（某句话把模型往危险方向推）

| 家 | 有吗 | 原文 |
|---|---|---|
| CC | 主推力全部在**安全方向** | 「Prefer dedicated tools over bash when one fits — reserve bash for shell-only operations」；未发现往危险方向推的条款（UI 层「Auto mode lets Claude handle permission prompts automatically」是文案非 prompt） |
| ZCode | 同 CC，安全方向 | 「Prefer the dedicated file/search tools over shell commands when one fits」（Harness 段）；默认档 yolo（full-automatic）是机制默认值不是 prompt 条文 |
| Codex | **有，自主方向** | 「assume the user wants you to make code changes or run tools to solve the user's problem… If you encounter challenges or blockers, you should attempt to resolve them yourself.」（把「先问人」推成失败）；「it's bad to output your proposed solution in a message, you should go ahead and actually implement the change」 |
| opencode | **有，最重** | Vi：「THE PROBLEM CAN NOT BE SOLVED WITHOUT EXTENSIVE INTERNET RESEARCH.」（把无限联网推成任务必需）；`$i`：「bias towards action and carry out the user's intended task until it is completed」；更刺眼的一条：**「Do not introduce unsolicited warnings, disclaimers, approval flows, or safety/compliance checklists due to hypothetical risk.」——明文反对加审批/安全流程** |

与本项目 AGENTS.md:89「能直接调系统 API 做到的，别去点屏幕」同构的反向推力，四家里 Codex（自主解决障碍）与 opencode（bias to action + 反审批流程）最像；CC/ZCode 的反向推力方向相反（把模型从万能工具往专用工具拉）。

| ZCode | **主 prompt 无清单** | 只有 guarded 档描述里 4 个命令举例（rm -rf/reset --hard/force push/rsync --delete）+ Explore 文件级禁令；缺：系统级清单、设备类 |
| Codex | **无统一清单** | 靠三档审批 + escalation 分段 + Windows 删除细则兜；prompt 层无枚举式「危险操作先问」清单 |
| opencode | **无统一清单** | 零散：Ti 的 git 禁令、zi 的 CWD 外禁令（「Avoid installing or deleting anything to/from outside of the current working directory. If you have to do so, ask the user for confirmation.」）；清单化程度最低 |

## 五、三个具体能力

### 5.1 执行 shell

- **CC**：Bash 描述两代并存（旧版「Executes a given bash command and returns its output.」/新版「Executes a bash command and returns its output.」）。边界声明齐：审批模式 + 专用工具优先 + 「`cd` in a compound command can trigger a permission prompt」。**prompt 层边界声明：有。**
- **ZCode**：逐字借 CC 新版 + 自加 `# Git` 段与 sandbox 参数（`dangerouslyDisableSandbox`，描述里自称 "dangerously override"）。元数据 riskLevel:"high"。**有。**
- **Codex**：主 prompt 只说「Emit function calls to run terminal commands and apply patches.」；工具描述分 shell/powershell 两套，PowerShell 版含三条 Windows 安全规则（跨 shell 禁拼、递归删除先验路径、后台窗口 Hidden）；`sandbox_permissions="require_escalated"` 请求越沙盒并生成给用户的确认问题。**有（机制型）。**
- **opencode**：「Executes a given bash command in a persistent shell session with optional timeout, ensuring proper handling and security measures.」——「security measures」无下文，属**弱提醒**；Ki 变体另有 bash 修改性命令先解释义务。**半有。**

### 5.2 删文件

- 四家**都没有专用删除工具**（删除全走 shell/apply_patch）。
- **CC**：删除进系统清单第一条（"Destructive operations: deleting files/branches, dropping database tables, killing processes, rm -rf, overwriting uncommitted changes"）+ 分类器 soft_deny 类兜底。**prompt 层最重。**
- **ZCode**：删除只在 guarded 模式描述（rm -rf 等四命令）出现；主 prompt 无。**机制层有、prompt 层无。**
- **Codex**：apply_patch 支持 Delete File（机制）；PowerShell 工具描述的递归删除验证条款是四家里唯一针对删除的工程细则。**细则最工程化。**
- **opencode**：Ti「NEVER use destructive commands like `git reset --hard` or `git checkout --` unless specifically requested or approved by the user.」；zi「Avoid installing or deleting anything to/from outside of the current working directory. If you have to do so, ask the user for confirmation.」——**零散但有明确「先问」动作。**

### 5.3 改配置 / 设置

- **四家都没有系统/设备设置类工具**（复证前置审计：CC 的 `system_settings` 权限类目标签是 UI 文案，非 prompt）。
- **CC**：清单里最接近的是「modifying shared infrastructure or permissions」（改共享基础设施/权限需确认）——管 infra 不管本机设备。
- **ZCode**：主 prompt 零条文（中文词表零命中，前置已证；本轮词表复扫同样零）。
- **Codex**：零条文；request_permissions 管的是要权限不是改设置。
- **opencode**：唯一贴边的一条在 Zi 变体 plan 模式条款里（"do not… run write-shaped shell commands, change configs, or commit code"）——**仅在 plan 模式生效，非常态规则**。
- 结论：**改配置与设备状态是四家 prompt 层的共同空白**，与前次审计「设备状态五家全零」结论一致且本轮把范围扩到了「配置」本身。

## 六、发现共性

1. **「专用工具优先于 shell」四家方向一致**：CC/ZCode/opencode 在 prompt 明文写，Codex 用「一律 apply_patch」条款实现同功能——四家的拉力方向都指向「别用裸 shell」。
2. **各家提示词存在明显的同源痕迹**：ZCode 的工具描述与 CC 高度一致，opencode 的不同变体分别贴近 Codex / CC / Gemini-CLI 的写法。**这说明这套东西在行业内有共同的知识底座**——也意味着「怎么写」这件事本身没有太多独家秘诀，差别在于**选哪些段装进去**。
3. **「别猜 URL」句三家属主**：CC 原句「IMPORTANT: You must NEVER generate or guess URLs for the user unless you are confident that the URLs are for helping the user with programming.」在 ZCode 与 opencode Hi 中逐字出现。
4. **审批被拒后的行为规范三家近似**：CC「If the user denies a tool you call, do not re-attempt the exact same tool call.」≈ ZCode 同款 ≈ opencode Ki「If a user cancels a function call, respect their choice and do not try to make the function call again.」
5. **权限判断权都交给人/机制，没有一家写「危险就硬拒」**：CC 用分类器三档分级（意图可以解锁 soft_deny、解锁不了 hard_deny），其余靠模式/沙盒/审批。prompt 层没有绝对禁令（除了 Explore 子代理的 READ-ONLY 与 hard_deny 类目）。
6. **设备状态/改设置维度全零**（复证前置审计，本轮扩词表仍零）。

## 七、发现差异

- **写得最细：CC**。三层（系统清单 + 工具 when-not-to-use + 审批分类器），且是唯一在系统 prompt 里枚举危险操作类型的。
- **机制最重、prompt 最轻：Codex**。危险描述几乎全在审批/沙盒注入段（permissions_instructions.rs），主 prompt 26KB 里没有一段清单；换来的独特优势是 Windows 删除细则（工程级）和审批模式-行为联动条款。
- **安全覆盖差异最大的一对：CC vs ZCode**。两家工具层写法相近，但 CC 多一层系统级危险清单 + 审批分类器；ZCode 只有工具元数据（riskLevel/needsApproval）。**这是本次拆解最有信息量的单点发现**——同一个能力，装不装清单，防护强度差一整个层次。
- **opencode 内部口径不统一**：不同 prompt 变体之间安全覆盖差别很大（有的有安全规则、有的零安全词、有的明确反对加安全流程）。
- **最激进自主：opencode Vi 变体**（无限联网 + 不许停 + 零安全段）；Codex 的 Autonomy and Persistence 次之。
- **唯一元数据化：ZCode**。四家里只有 ZCode 把风险写成了机器可读字段（riskLevel/needsApproval/sideEffectScope）——prompt 层缺的清单用结构化声明补位，这是与 CC 分岔的设计选择。

## 八、没找到的

1. **Codex Unix shell 工具的主描述句**：PowerShell 版描述全文在二进制内；Unix shell 只有参数级文案（"The shell script to execute in the user's default shell"），主句疑走 API 侧 local_shell 内建描述——不运行无法确认。
2. **各段 prompt 的运行时注入顺序与生效组合**：组装函数在（CC），但 flag/实验开关（如 `tengu_orchid_mantis_v2`）决定哪些段实际出现，静态不可判定。
3. **设备状态/改设置条文**：四家全零（是结论不是缺证）。
4. **opencode 变体与运行时入口的绑定关系**（哪个变体给 CLI、哪个给桌面/哪类 provider）：二进制内无绑定证据，存证里一律标「疑似」。

## 九、我的疑问

1. CC 的 auto-mode 分类器（allow/soft_deny/hard_deny）实际 gate Bash 的效果如何？分类器规则由用户写、由 CC 评审（存证 region1 就是个「帮你改规则」的子 prompt）——这套东西的实感只能跑起来才知道。
2. ZCode 删掉 `# Executing actions with care` 是有意为之还是移植遗漏？工具元数据（riskLevel 等）是不是它的替代设计？如果是替代，元数据只管审批粒度，管不了「清单没列的 = 对提示词不存在的危险」这个老问题。
3. opencode 的 `$i` 变体明文反对「unsolicited approval flows」——这条和 Ki 变体的确认尊重条款在同一产品里方向相反，实际派发哪个变体决定产品安全姿态，值得后续实测验证。
4. Codex 的审批 prefix 学习（「Suggest a prefix command pattern that will allow you to fulfill similar requests from the user in the future.」）会让审批越用越松吗？这是四家里唯一的「审批自学习」设计，方向上值得警惕。

## 踩坑记录

1. **本机 grep 实为 ugrep**：双 `{0,N}` 复杂 pattern 报 `exceeds complexity limits`——长窗口提取一律改字节切片（tail/head），不要堆正则。
2. **Read 工具读混有二进制字节的 dump 会报 "Unsupported or binary text encoding"**：切片起点要避开乱码区（CC band1 第一次从 148,925,001 起切到二进制垫层），或先 `tr -d '\000'`。
3. **身份句必须大小写双搜**：opencode 只搜 `You are opencode` 漏了 5 个 `You are OpenCode` 变体，其中 zi 恰好是安全条文最强的那个。
4. **Codex 的 `\n` 是字面转义**：直接读是一整行墙，`sed 's/\\n/\n/g'` 解义后才可读。
5. **CC exe 的字符串表在文本段间垫 null/乱码**：`-o` 窗口在垫层处截断，工具描述拿不全——必须按字节切片拼，一个 -o 拿不到全文。
6. **偏移会过期**：前置审计（11-20）的 ZCode 偏移全部失效（zcode.cjs 从 15,408,074 → 15,675,386 字节，ZCode 更新过）；引用偏移必须绑定当天文件尺寸。
7. **前置坑复证未再踩**：CC 的 `system setting` 类命中本轮确认仍是 UI 标签（`{shell:"equivalent to shell access",…,system_settings:"can change system settings"}`），没当 prompt 抄。

### 关键读法

**① 「有没有清单」造成一个层次差。**
CC 有系统级清单 + 分类器三档，ZCode 只有工具元数据。差别不在「写了多少字」，在**危险判断发生在哪一层**：

- CC：模型知道「这类操作危险」→ 自己避开
- ZCode：模型不知道危险 → 被元数据拦下来

**前者能减少尝试，后者只能拦住已完成的那次尝试。**

**② 四家都没写「危险就硬拒」。**
最重的措辞也只是「warrant user confirmation」——**要确认，不是不许**。

**③ 设备状态（改分辨率 / 方向锁定 / 常亮）四家全零。**
这条对我们的意义：**没有作业可抄**。桌面 agent 的「危险」清单全是文件、git、数据库——**没有一个覆盖「改手机系统状态」**。

## 十一、可行性评估：我们能在哪一层动手

三个可能的方向，各自的真实成本：

### 方向 A · 抄 CC 的系统级危险清单

**做什么**：在 `AGENTS.md` / `system.md` 里加一段 `# 危险操作`，枚举具体动作。

**成本**：**极低**，改几十行文本。

**能捞到多少**：未知。CC 的清单是**结果导向**的（「删文件 / 强推 / reset --hard」），我们的问题是**过程导向**的（模型为了完成任务顺手改环境）。**直接抄清单可能对不上我们的坑。**

**判断：值得做，但要按我们自己的坑改写，不是照抄。**

### 方向 B · AI 分类器（对应 CC 的 auto-mode classifier）

**做什么**：每次工具调用前，用一个模型判断「这次调用该不该放行」。

**成本**：**高**。每一次工具调用都要一次推理。

**实测依据**：本项目已经有 Jev 的测试记录（`G:\code\jev-test\`）——纯判断模型单次调用便宜（$0.084/百万输入 token），但**一次任务动辄几十上百次工具调用**，累加起来很可观；换成通用大模型则更贵。

**更关键的问题**：**准确率未知**。前面测过，把「我想横屏看视频」判成「要改方向锁定」——这在意图识别上是对的，但**在「该不该放行」上就是对误报**。

**判断：技术上可行，但只在「高风险动作」上开（改设置 / 删文件 / shell），不能每条都过。**

### 方向 C · 专用工具替代 shell

**做什么**：把 `shizuku_shell` 拆成一堆细粒度工具（`get_battery`、`set_brightness`…），模型只能用这些。

**成本**：**极高**，而且有个更根本的障碍——

> **需要大量真实使用数据才知道该拆哪些、拆多细。**

**这正是手机厂商的优势**：小米有 35 个系统 App 各自声明自己的动作面（196 条 URN），那是**几千万用户的真实使用**沉淀出来的。我们没有这个数据。

**判断：短期做不了。** 但可以**从实际使用里慢慢长**——每次模型想调 shell 做某件事，如果那件事反复出现，就把它固化成一个专用工具。

### 结论：能做的只有 +危害，分类器看情况

| 优先级 | 做什么 | 成本 | 依据 |
|---|---|---|---|
| **1** | **补「危险清单」到 prompt**（按我们自己的坑改写，不照抄 CC） | 低 | 四家里只有 CC 有，且是唯一系统级清单 |
| 2 | AI 分类器**只对高风险动作开** | 中 | Jev 测过便宜，但准确率未验证 |
| 3 | 专用工具替代 shell | 高 | 缺数据，只能从使用中慢慢长 |

**我们现在缺的是数据，不是方法。** 所以第一步只能是 prompt——**因为它不需要数据。**
