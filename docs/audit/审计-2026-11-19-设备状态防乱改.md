## 步骤 4 · dsh-go 判定层

> 框架默认行为先答（坑 3）：dsh-go 是 Flutter/Go 宿主 + Kotlin 原生操控层。Flutter 框架对「改系统设置」没有任何默认行为（框架连这个 API 都不碰）；所有设备动作判定都在 Kotlin 的 phone/ 包里显式实现，Go 引擎侧只负责把工具调用递过去（全仓 Go 代码无设置写路径，本轮已 grep 验证）。**「它没写」在这里就是「没有」，不存在框架兜底。**

### 4.1 ConfirmMode 三档语义（SafetyGate.kt:87-100；默认档 PhonePolicies :11）

| 档 | 语义 | 哪些动作会问 |
|---|---|---|
| `ASK`（"ask"，**默认**，:89） | 关键步骤先问 | 每 App 第一步（firstInApp，:265/:279）、敏感词命中（:266 → reason "sensitive:…"，:274）、every-write 名单 App（:264，默认微信 :165）、无元素依据的 tap_xy（:261-262/:271-272）、TYPE+submit（:273）；**其余放行**（:277 else → Allow） |
| `TASK`（"task"，:92） | 本任务免确认 | 第一张确认卡提供「本任务不再询问」（offerTaskWaiver :281，仅 TASK 档给）；授予后本任务普通动作免问（waived() :313-314），**硬规则与不合格 tap_xy 不豁免**（:263 `waived && !forceOnce` 才 Allow） |
| `ALWAYS`（"always"，:95） | 始终免确认 | 普通确认全免（waived() :313）；硬规则（:248-258）与 forceOnce tap_xy（:262）仍生效 |

三档都拦的硬规则（docstring :82-85「Whatever the mode, the hard refusals still apply」）：own-app :248、deny-list :249（默认 30 个银行/券商/支付包 :150-162）、system-page :251-254、secret-field :255-258。例外：KEY 永远放行（:245，注释「back / home / recents / shade: always a way out」——刻意保留退出通道）、SCROLL 永远放行（:250）。

### 4.2 「系统设置页只读不写」到底拦什么（SafetyRules :127-147 + checkWrite :251-254）

判定依据 = **前台包名 ∈ SYSTEM_PACKAGES**（:132-145，settings / SystemUI / permissioncontroller / packageinstaller / 各 OEM 安全中心 / keychain 等约 25 个包）。命中时拒绝一切写动作：文案「系统设置 / 权限 / 安装页（「$app」）只看不动。请 handoff 让用户自己完成。」（:253）。

**它拦的是「在系统设置 App 的界面上动手」（tap/type），不是「写设置项的值」。两者必须分开：**

- **打开设置 App：不拦。** `checkOpen`（:220-226）只查 own-app 和 deny-list，`com.android.settings` 不在其中；intent 工具本身就带 settings 类目（PhoneToolCatalog.kt:35-39，`INTENT_KINDS` 含 "settings"、`SETTINGS_PAGES` 14 个页面）——开设置页看状态是设计内行为。读取也放行（:127-131 docstring「the agent may read but never act」）。
- **shell 写设置项：不经过这道闸。** `settings put` 走 android_shell 工具链（PhoneCore.kt:370 → :393-411 → PhoneAndroidShell.run），checkWrite 只判 UI 动作，对 shell 命令无 key 级判定。dsh-go 挡的是「手碰到设置页」，挡不住「命令改设置值」——命令层的唯一约束是每条完整命令人工确认（见 4.3）。

### 4.3 PhoneAndroidShell 确认之后记不记原值（PhoneAndroidShell.kt:50-56）

确认框展示**完整命令原文 + 实际身份**：prompt 文案「执行 Android 系统命令（%backend，UID %uid）……仅允许本条命令：\n\n%完整命令」（:49-52）；身份白名单 adb=UID 2000、shizuku=UID 0/2000（:47）；`offerTaskWaiver = false`（:54）——**UI 侧的本任务/始终免确认对 shell 刻意无效**（docstring :9「A separate one-command grant: UI app/task waivers deliberately have no effect here」），只认 `ALLOW_ONCE`（:58）。

**不记原值。** 全文件 62 行无任何读取/暂存设置值的动作；executor 接口（:4-7）只有 command + confirm 回调 + 输出结构。确认的是「你亲眼看见了这条命令」，不是「它改了哪个 key、改之前是什么」。工具描述也明说「超时或取消不撤销已产生的副作用」（PhoneToolCatalog.kt android_shell 条目）；PhoneCore.kt:398 把每次 shell 调用 `skillTrace.markIncomplete(…Gap.UNCERTAIN_RESULT)`，禁止把任意系统副作用烘进「可回放技能」。设计动机的文档来源：docs/guide/zh/04-phone-control.md:38（「每条命令原生确认完整命令和实际身份……系统授权、后台屏幕授权或恢复无障碍授权，都不等于允许任意系统命令」）。

### 4.4 ControlOverlay 30 秒超时对长时间任务的含义

- 数值链：ConfirmRequest.timeoutMs 默认 30_000（PhoneContracts.kt:232）→ 确认卡上限硬钉 30_000（PhonePrompts.kt:77 `coerceIn(1, 30_000)`）→ 超时 `pending.resolve(Decision.DENY)`（ControlOverlay.kt:281 `pending.await(request.timeoutMs + 1_500) ?: …`）→ 模型收到「用户拒绝了这一步（或 30 秒内没有选择）。不要重试同一个动作」（SafetyGate.kt:367）。手册同口径：guide/zh/04-phone-control.md:91「确认卡 30 秒不选按拒绝处理」。
- 含义：**每个需要确认的动作最多给人类 30 秒。** 无人值守的长时间任务会在第一个确认点停下且被明确禁止原样重试。豁免通道（TASK/ALWAYS）只作用于 UI 动作；android_shell 永远逐条确认（:54）。**效果 = 事实性限速器：没人盯着就干不了需要确认的事；代价 = 人在场也必须 30 秒内回应，长确认卡（如 shell 命令审读）会紧张。**

## 步骤 5 · dsh-go 记录层与还原层

- phone/ 全目录 grep `snapshot|revert|rollback|restore`（*.kt）：命中全部是 **UI 屏幕快照**（ScreenSnapshot、PhoneTasks.Snapshot 任务状态、skill replay 的同次后读）——「快照」一词在 dsh-go 里专指屏幕/任务状态，无一处指设置值。
- Go 引擎侧（runtime/ sdk/ services/ packages/，*.go）同关键词：**零命中**。
- **PhoneTasks.kt:296 「scope changes revoke rather than restore history」≠ 设置还原**：该注释属 :297-304 `syncVisualScope` / `visualScopes` / `visualGrants`——是**截图点击授权作用域**的管理（作用域变了 → 授权移除，不回放历史授权），属权限回收。已按任务书要求与「设置还原」明确区分，不混为一谈。
- 唯一一处真实写设置：BackgroundControl.kt:1482-1483 `Settings.Global.putInt(adb_wifi_enabled, 1)`——App 自身拉起无线 ADB 的 bootstrap（:1482 先查 DEVELOPMENT_SETTINGS_ENABLED），不面向 agent、无还原记录。
- PhoneTaskJournal.kt 定性（:3 docstring「The logical interruption record only. No payload, replay or physical-resource receipts」）：只记「任务被中断过」的 token，**不是动作审计账本**。
- 结论：dsh-go 对「设置项原值」的记录层与还原层**根本没实现**。它确认做得重（每条 shell 命令人审），但确认过后和 dsha 一样——**写出去就收不回来**。

## 步骤 7 · 最小可行补法（在 dsha 现在的代码结构里）

> 前提：三个收法本身的取舍 docs/权限.md §6.17 ⑥（:873-879）已论证过（倾向 B 做地基 + C 做授权），这里不再重新论证，只回答「哪个最容易落地、落地后挡住哪几个类目」。假阳性风险按 §6.17 ③「参数没定、没验证过」的口径如实标注：**以下所有假阳性率都是估计，均未验证**。

### 方案 A · 设置写白名单 fail-closed —— 最容易，半天止血

- **改哪个文件**：`GuardImpl.java` 的 `Act.setting`（:426-442）。
- **加什么**：新增第三张表 `Set<String> SETTING_WRITABLE`（结构照抄 FOUNDATION/EXPERIENCE 现成的 HashSet 模式，:55-69）；把 :441 第三档从「空 Act 放行」改成「不在 SETTING_WRITABLE → `Act.deny`，文案列出当前可写清单」。`classifyShell` 的 SETTINGS_PUT 分支（:271-274）已把 key 送进同一个 `Act.setting`，**shell 路径零额外改动自动继承**。
- **判据/验证**：单元测试——对 `stay_on_while_plugged_in`、`accelerometer_rotation`、`user_rotation` 分别以 `/setting` 端点与 `settings put` 命令两种形态过 `GuardImpl.check`，期望 deny（或清单内 ask），**不得 allow**。可全离线验证，不需要真机。
- **假阳性风险在哪**：清单完备性——清单外的一切合法写全被拒。dsha 自己的工具描述就推荐了 10 个 key（index.js:476-477：亮度/亮度模式/超时/旋转/字体/四音量/触摸音/震动/通知灯/铃声），这批必须先入清单；遗漏的合法 key 会让任务卡死，fail-closed 的代价就是「宁可卡住」。缓解：deny 文案带清单让模型自查换路。
- **挡住**：B、C 两类目（settings-put 形态）。**挡不住**：A（wm 不走 settings put）、D。
- **排期**：**P0，估时 0.5 天**。

### 方案 A' · shell 兜底分支 allow → ask —— 和 A 同文件，一起做

- **改哪个文件**：`GuardImpl.java` 的 `classifyShell` 兜底（:296-297）。
- **加什么**：兜底分支不再无条件 `Act.simple("shell.exec", true)`，对**不匹配任何已知读模式**的命令改 `Act.forceAsk`（「未识别的特权命令需要确认」+ 命令原文）。读动词白名单（`get|list|dumpsys|getprop|ps|ls|cat|logcat|screencap` 等）先于兜底放行。dsha 已有全套确认框基建（Consent.java），只差这一处判断。
- **验证**：单元测试——`wm size 1080x2400`、`svc power stayon true` 期望 forceAsk；`settings get global aaa`、`dumpsys battery` 期望放行。
- **假阳性风险在哪**：读动词清单漏项 → 合法读被弹框（烦人但无害，弹框可放行）；变形写法绕过读动词伪装（§6.17④「正则拦不住变形」的老洞）——所以 A' 是**把关升级不是关门**，真正的门是 A 的 key 表。
- **挡住**：A、B、C 的 shell 路径（从静默放行升级为人审可见——对齐 dsh-go 现状）。D 仍不解决。
- **排期**：**P0，估时 0.5 天**（与 A 同一文件同一批测试）。

### 方案 B · 快照-账本-还原 —— 钩子点现成，最值得做

- **改哪个文件**：①新增 `SettingsSnapshotStore`（guard 包，账本格式直接按 §6.18 :925 的字段：key / 命名空间 / 原值 / 触发指令 / 时间）；②`MainActivity.handleSettingRequest`（:2921-2948）写前读原值并落账本（:2939-2942 的 put 前插 `Settings.System.getInt/getString`，读不到也要记「未设置」）；③`classifyShell` SETTINGS_PUT 命中时由 App 侧先跑 `settings get <key>` 读原值（App 有 shell 通道）；④还原入口挂任务生命周期（SessionAdmin / 会话空闲钩子）：按「本次任务改过的键」逐个写回原值，**还原动作本身过一次 ask**（把还原做成可见动作而不是静默回滚）。
- **判据/验证**：写 3 个 key → 账本文件出现 3 条含原值记录 → 触发还原 → `settings get` 逐一回原值。**需真机验证，本轮未验**（本轮不变量禁止任何写操作）。
- **假阳性风险在哪**：还原冲突——用户在任务期间合法改了同一 key，任务结束还原会覆盖用户的选择（§6.17 :881 已自认未解）。缓解：还原范围限定「本次任务改过的键」+ 还原前 ask 列出 diff 让人过目——**冲突判定从「自动还原」降级为「人看一眼」，参数没定的老问题就不需要参数了**。
- **挡住**：D 类目（记录层 + 还原层从零到一）；A/B/C 的 settings-put 形态从「改了收不回」变成「改了能收回」。**诚实标注记录不了的**：`svc power stayon` 是非持久行为、无 get 对应，记录不了原值（只能靠 A' 的人审兜）；`wm size/density` 原值不在 settings 里，要解析 `wm size` 输出，**P2 再做**。
- **排期**：**P0-P1，估时 2-3 天**（账本 + 两个钩子 + 还原 + 冲突规则）。文档倾向（§6.17 :879「B 做地基」）与本审计结论一致。

### 方案 C · 任务书显式授权 —— 只能当开关，单独上没意义

- **改哪个文件**：引擎侧系统提示/工具描述约定 + `Guard` 加任务级状态位（模式照抄 `Consent.isPending` 的互斥实现：Consent.java:66-69 的 synchronized 单标志，换成「本任务允许改环境 + 允许的 key 集合 + 有效期」）。
- **加什么**：①约定改环境前必须在任务书/回复中显式列出 key + 值 + 还原计划；②`Act.setting` 第三档在无授权时 deny、有授权且 key 匹配时放行——**C 是 A/B 的授权开关，不是独立防线**。
- **判据/验证**：无授权任务书 → 改 accelerometer_rotation 被 deny；带 key 级授权 → 放行且账本记下授权来源。
- **假阳性风险在哪**：授权粒度——「允许改环境」一句全放等于没放（§6.17 :877 原话「可能诱发绕路」）；模型忘写授权 → 合法任务被卡。缓解：授权必须 **key 级**，不接受 umbrella 授权。
- **挡住**：单独用**一个类目都挡不住**（模型可以不写授权，prompt 约束被绕过在 dsh 生态有实证——§6.17④「正则当门」同族教训：拦得住明写的，拦不住变形的）。
- **排期**：**P2，估时 1-2 天**，依赖 A/B 的数据结构先落。

### 推荐组合与理由

**A + A'（P0，合计 1 天）止血 → B（P0-P1，2-3 天）补根 → C（P2）做授权开关。**

1. A+A' 一天内把 B/C 类目的「静默放行」变成「默认拒」、把 shell 路径从裸奔拉到 dsh-go 的人审水平——止血最快，两处改动都在 GuardImpl 一个文件里，结构现成（第三张表 + 兜底分支改 ask）。
2. B 的钩子点（handleSettingRequest :2939-2942 与 SETTINGS_PUT :271-274）**key 都已被提取出来**，挂记录是纯增量；它是唯一同时解决 D 类目（记录+还原从零到一）的方案，也呼应文档既定倾向「B 做地基 + C 做授权」（§6.17 :879）。
3. C 单独上挡不住任何类目（可绕），必须踩在 A 的清单和 B 的账本上才有落点——所以放 P2。
4. 残余漏洞的诚实清单：`wm size/density` 的原值记录（P2）、`svc power stayon` 的原值记录（记录不了，靠 A' 人审）、rish 直连绕过正则（GuardImpl.java:18-19 自认，需要 App 外一层，§6.17 :883 自认未解）——**这三个洞修完 A+A'+B 仍然在，不要假装修完了**。

## 步骤 8 · 它做对了、我们该抄（和别指望抄的）

### dsh-go 有、dsha 没有（针对四类目）

1. **shell 通道的「豁免隔离」设计**（最该抄的一条）：UI 侧的本任务/始终免确认对 android_shell **刻意无效**——docstring 明说「A separate one-command grant: UI app/task waivers deliberately have no effect here」（PhoneAndroidShell.kt:9），实现上 `offerTaskWaiver=false`（:54）、只认 `ALLOW_ONCE`（:58）、backend/uid 白名单（:47：adb=UID 2000、shizuku=UID 0/2000，防意外身份）。对 B/C 类目意味着：**用户可以放心开免确认省弹框，shell 这条危险通道仍然逐条人审**。dsha 的 shizuku_shell 默认全免（index.js:243/:276-294），豁免一旦打开（如果做方案 C）必须学这条隔离。**抄法（不抄代码）**：dsha 在 `GuardImpl.classifyShell` 里对特权 shell 保持独立于任何任务级豁免的 forceAsk 路径。
2. **「副作用不可撤销」的诚实声明 + 禁止烘进技能回放**：android_shell 工具描述明写「超时或取消不撤销已产生的副作用，结果不明不可自动重试或切通道重放」（PhoneToolCatalog.kt android_shell 条目），且调用侧 `skillTrace.markIncomplete(…Gap.UNCERTAIN_RESULT)`（PhoneCore.kt:398）阻止 shell 效果被固化成可自动重放的操作序列。dsha 的 shizuku_shell 描述无此声明。这是文案+一行标记的零成本改动，直接降低「失败了换个姿势再试一遍」的二段伤害。

### dsha 有、dsh-go 没有

1. **key 级判定表**：SETTINGS_PUT 提取 key 送三档分类（GuardImpl.java:82-83 → :426-442），FOUNDATION/EXPERIENCE 两张表可审计、可测试、不依赖人眼。dsh-go 对 shell 命令**没有**任何 key 级判定（只有命令原文人审，PhoneAndroidShell.kt 全文无 key 提取）。dsha 的问题只是**表覆盖不全 + 第三档默认放行**——机制方向是对的，方案 A 就是把这张表补全。
2. **前台读不到就 fail-closed 的不变量**：「读不到前台包名 → deny」（GuardImpl.java:151-154，注释「不变量 ④」）+ 判定异常一律 deny（Guard.java:94-99「承重墙」注释）。dsh-go 的 SYSTEM_PACKAGES 是静态清单匹配，无「读不到 = 拒绝」兜底。这条哲学对 D 类目同样适用：记录缺失本身就该当作异常态，而不是静默继续。

### 两家都没有（别指望从任何一家抄）

**设置项的记录层与还原层——两家都是零。** 证据：dsha 全仓 grep 无（步骤 3.1）、账本待办未勾选（docs/权限.md:924-925）；dsh-go phone/ + Go 引擎侧 grep 无（步骤 5）、PhoneTaskJournal 自述只记中断 token（PhoneTaskJournal.kt:3）、工具描述自认「不撤销已产生的副作用」。**还原层必须从零写**——这就是推荐组合里 B 是主体的原因。次级缺口（两家都没有、影响较小）：拒绝文案都不带「不要重试同一动作」语义（dsh-go 有，SafetyGate.kt:367；dsha 的 Consent 文案无——这条其实 dsh-go 有，从它那抄文案，一行改动，P2）。

### 踩坑记录

### 坑：任务书给的路径是约数，ControlOverlay.kt 第一次按 phone/ 直下查扑空
- 根因：ControlOverlay.kt 实际在 `phone/a11y/` 子目录，任务书写的 `ControlOverlay` 只给了类名没给全路径。
- 解法：先 `find` 定位再读，没有猜路径硬读。
- 下次怎么避：任务书里的文件路径一律当作「线索」不当「坐标」，动手前 find/glob 确认一次。

### 坑：Git Bash grep 模式里带转义引号直接零命中
- 根因：`grep -n "\"/setting\""` 的双引号转义在 Git Bash 里被 shell 吃掉，模式失真，第一次查 MainActivity 路由返回空——差点误判「/setting 没有服务端处理」。
- 解法：简化模式（`grep -n "setting\|/shell"`）重查，命中后再精读行号区间；零命中一律换一次写法再下结论。
- 下次怎么避：Windows Git Bash 下 grep 模式先最短化，含引号的模式改用单引号包裹或拆开查；「零命中」本身需要二次验证才算证据。

### 坑：MEMORY.md 索引超 40k token，整读超限
- 根因：索引文件按设计应一行一条，但近期条目膨胀成超长段落，全读超过单次读取上限。
- 解法：读首页部分拿到待办与近期变更即止，没有硬读全文；本次任务相关记忆（dsh 审计前档）通过仓库内既有报告（审计-2026-11-10、对比-2026-11-16）补齐。
- 下次怎么避：开场对超大索引先读头部 + 按关键词 grep（本次场景用 `dsh|审计|权限`），不做全文阅读。

### 坑：dsh-go 的「快照」一词全是屏幕语义，按字面搜会污染判断
