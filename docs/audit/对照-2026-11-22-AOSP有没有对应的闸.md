## 一句话结论

**四段里 AOSP 给了 2.5 段**：② 能力表校验**有**（AppSearch 查表 fail-closed，和小米 actionMap 同构，直接用）；③ 执行器路由**框架层有**（精确 functionId 路由 + 无平台兜底 + 执行器只能被 system_server 调），但 App 内「无 default 写」纪律还是我们自己的代码；① 表达层闭集**部分有**（声明制闭集机制 = 小米 DDF 同构，但平台没有语义词汇表、执行期不校验参数）；④ 幂等 + caller tag 审计**基本没有**（只有 uid 级 statsd 埋点，幂等/来源串/限流全要自己写）。

一句话：**AOSP 把「闸的机械结构」造好了，把「闸的纪律」留给应用自己**——而小米实证里的四段，恰好一半是机械结构（②③框架侧），一半是纪律（①词汇表、③App 内 switch、④幂等审计）。

## 二、① 表达层闭集

**部分有。机制有，词汇表没有，执行期参数校验没有。**

### 1. 调用面形状：没有「写任意 key」的表达形式

`ExecuteAppFunctionRequest` 只有四个字段（`core/java/android/app/appfunctions/ExecuteAppFunctionRequest.java:63-93`）：

- `targetPackageName`：目标包名
- `functionIdentifier`：函数 ID（字符串，唯一性按包内）
- `parameters`：GenericDocument（参数）
- `extras`：Bundle

**协议里不存在「写任意 settings key」的表达形式**——平台不提供任何通用设置写函数。这一点比小米还干净：小米旧协议有 `System.SetMiuiDatabase` 四元组任意写缺口（前置实证 §1.3⚠️），AOSP AppFunctions 的平台层连这个缺口的原语都没有。

### 2. 函数 ID 天然是闭集，但闭集内容 = 声明

模型侧调用方可以传任何字符串 functionId，但传了表里没有的 ID，调用在②的查表处 fail-closed（见下节）。**模型可表达的上限 = 「调一个表里声明过的 functionId + 传参数」**。所以表达层闭集不用单独造——它是声明机制的自然结果，这印证了坑预判 1：①和②是同一件事。

### 3. 语义词汇表：平台不定义，应用各管各的

AOSP **没有** `switchautorotationmode` 这种平台级语义动作枚举。语义动作由目标 App 自己声明：

- 应用用 Jetpack AppFunctions SDK 的 `@AppFunctionDeclaration` 注解函数（`appfunctions_doc.txt:612-634` 示例：`createCalendarEvent(title: String, startDateTime: LocalDateTime): Event`）
- 注解处理器 build 期生成 XSD 放进 app assets（`appfunctions_doc.txt:647-650` "The AppFunctions Jetpack library generates an XML schema file that lists all the declared AppFunctions"）
- 设备上系统扫描索引

对比小米：小米有统一 URN 词汇表（`urn:aiot-spec-v3:com.mi.phones:action:[包/服务/动作名]`）+ 云端 DDF 扩充；AOSP 是「各 App 各自声明、无全局词汇表、无云端下发面」。**做我们自己的助手时，语义词汇表（函数集怎么命名、粒度多粗）要自己设计**。

### 4. 参数：声明有类型，执行不校验

- 声明侧 XSD 是类型化的：`AppFunctionSchemaParser.java:206-254`（packages/modules/AppSearch）解析 `xs:string / xs:long / xs:int / xs:boolean / 嵌套 appfn: 文档类型`，并给 AppSearch 建 schema。
- 执行侧参数是 GenericDocument，文档自己承认不校验：`ExecuteAppFunctionRequest.java:79-81` 与 `:123-125` 两处明说 "The document may have missing parameters. Developers are advised to implement defensive handling measures."
- **executeAppFunction 全链路没有任何参数 schema 校验代码**（见下节调用链）——类型只进了索引（用于发现），不进执行闸。

对比小米：DDF 的 in 参数类型化、SpecParser 校验动作支持性。参数值级校验两边其实都在执行器侧——但小米 DDF 至少有类型契约可查，AOSP 的执行期校验是零，要自己写。

## 三、② 能力表校验

**有，直接用。与小米 actionMap 同构：查不到即拒绝，fail-closed。**

### 1. 表怎么建（构建链）

```

  → Jetpack SDK build 期生成 XSD 进 app assets
  → 包变更/开机时 AppSearch AppsIndexer 解析
      AppFunctionSchemaParser.parseAndCreateSchemas (AppFunctionSchemaParser.java:103-136)
        从目标 app assets 读 XSD；解析失败/无 AppFunctionStaticMetadata schema → 空 map
        （= 该 app 一个函数都没有：索引侧 fail-closed）
      :73-87  mMaxAllowedDocumentType 上限（防恶意 app 塞爆 schema 类型）
      AppFunctionStaticMetadataParserImpl.parseAppFunction (:211-280)
        字段：function_id / schema_name / schema_version / schema_category /
              enabled_by_default / restrict_callers_with_execute_app_functions /
              display_name_string_res

        :164-167, :193-196 mMaxAppFunctions 单 app 函数数上限
  → 存入 AppSearch "apps-db"（AppFunctionStaticMetadataHelper.java:49-50）

```

### 2. 运行时副本（static → runtime 同步）

`MetadataSyncAdapter.trySyncAppFunctionMetadataBlocking`（`services/appfunctions/java/com/android/server/appfunctions/MetadataSyncAdapter.java:147-209`）：static 表 diff 出 added/removed，同步到 runtime 表。触发点：

- 用户解锁时 `AppFunctionManagerServiceImpl.onUserUnlocked`（`AppFunctionManagerServiceImpl.java:119-124`，:538-554）
- static 表变化的 observer 回调（`:577-622`，监听 "android" 包的 apps-db 变更再触发 sync）

### 3. 调用时的校验链（⭐ 核心链路）

### 4. 查不到会怎样（小米对照）

- 小米：`actionMap.get(urn)==null` → 日志 "action not in actionMap" → **从执行队列删除**（静默丢弃）
- AOSP：documentId 查不到 → **返回错误码**给调用方（非 TRUSTED 调用者路径 = ERROR_FUNCTION_NOT_FOUND(1003)；TRUSTED 路径的 not found = ERROR_SYSTEM_ERROR(2000) 带消息——错误码粒度毛边，见踩坑 5）
- 都是 fail-closed，都到不了执行。AOSP 没有队列概念（同步 Binder 调用 + 回调），「从队列删除」对应物就是「返回错误」——AOSP 的失败**更响**（调用方立刻知道），小米的更静默。

## 四、③ 执行器路由

**框架层有：精确路由 + 无平台兜底 + 执行器只能被 system_server 调。App 内「无 default」纪律要自己写。**

### 1. 框架没有任何兜底执行路径

`AppFunctionManagerServiceImpl` 只做四件事：caller 校验 → AppSearch 查表 → 解析+绑定目标 service → 转发。**框架代码里不存在任何「平台替应用执行动作」的路径**（对照小米 URN→专用方法 switch 在 Settings App 内）。真正的执行永远发生在目标 App 自己的进程里。

### 2. 路由目标与双向身份验证

- 目标 = 应用声明的 `AppFunctionService` 子类，SERVICE_INTERFACE = `android.app.appfunctions.AppFunctionService`（`core/java/android/app/appfunctions/AppFunctionService.java:63`），manifest 里必须声明 `android:permission="android.permission.BIND_APP_FUNCTION_SERVICE"`（`:44-50` javadoc 模板）
- 系统侧：`ServiceHelperImpl.resolveAppFunctionService`（`ServiceHelperImpl.java:41-56`）——解析不到或不带该权限（`:54`）→ null → ERROR_SYSTEM_ERROR
- 执行器侧：`AppFunctionService.createBinder`（`:96-99`）`checkCallingPermission(BIND_APP_FUNCTION_SERVICE)` 不满足直接 SecurityException **"Can only be called by the system server."**

对照小米 `AiActionUtils.checkPermissions`（`getCallingUid→包名==com.xiaomi.aicr`）：AOSP 的对位物更通用——**执行器只信 system_server**，而 system_server 已经完成了 caller 校验，执行器拿到的是经过验证的 `callingPackage`（`:91-95` 参数透传）。「挡借刀」这层 AOSP 白嫖。

### 3. App 内分发：抽象方法，无 default，也不禁 default

- `onExecuteFunction` 是抽象方法（`AppFunctionService.java:177-184`），App 按的是哪个函数由 `ExecuteAppFunctionRequest.getFunctionIdentifier()`（`:162-163`）给出，**App 必须自己写 switch/when 分发**
- 框架不提供 default 实现，也**不阻止** App 写一个「functionId 认不出就通用写」的 default——这正是小米③纪律（URN 稀疏开关无 default、`doActionForSwitchAutoRotationMode` 专用方法）所在的位置，也是我们抄纪律的地方
- 未捕获异常框架代答：`:118-123` 异常包成 `AppFunctionException.ERROR_APP_UNKNOWN_ERROR(3000)` 回给调用方——不会崩掉绑定

### 4. 生命周期保险（小米没提、AOSP 白送的）

- `CancellationSignal` 全链路（caller 取消 → `RemoteServiceCallerImpl.java:122-127`）；caller 进程死亡 → 服务取消（`:128-137` linkToDeath）
- 取消后 5s 强制 unbind：`ServiceConfigImpl` `execute_app_function_cancellation_timeout_millis` 默认 5000ms（DeviceConfig 可调）
- 绑定死亡/空绑定/onBindingDied 全部落 `onFailedToConnect`（`:153-168`）

## 五、④ 幂等与审计

**基本没有。只有 uid 级 statsd 埋点；幂等、来源串、限流全部要自己写。**

### 1. 审计：有埋点，粒度粗

- hook 点：`SafeOneTimeExecuteAppFunctionCallback` 完成回调（`AppFunctionManagerServiceImpl.java:157-172`）——成功/失败都会触发
- 内容：statsd atom `APP_FUNCTIONS_REQUEST_REPORTED`（`AppFunctionsLoggerWrapper.java:43-63`），字段 = `callingUid + targetPackageUid + errorCode + requestDataSize + responseDataSize + latency`，6 个
- **没有 functionId、没有 caller 包名字符串、没有结果内容**。atom 定义本体在 proto_logging（本地 clone 无命中，见 §九）；字段清单以调用点 6 参数为准
- dump：`AppFunctionDumpHelper.java:121-146` 只 dump 能力表状态（static+runtime 元数据联表打印），**不是调用历史**

### 2. caller tag：transport 有身份，写入侧没有

- 框架把经过验证的 `callingPackage` 透传给执行 App（`AppFunctionService.java:91-95`）——执行器**拿得到**调用者身份
- 但框架不把来源附加到任何写入记录——写入发生在目标 App 自己的代码里，小米那种 `RotationPolicy.setRotationLock(ctx, want, "AiAction#doActionForSwitchAutoRotationMode")` 进 framework 日志的来源串，**要我们在自己的执行器里自己设计**（写入前拼来源串 → 进我们自己的 action log）

### 3. 幂等：没有

- 全链路无请求 ID、无去重、无状态比对。同一调用重复执行 = 重复执行
- 小米的 `want == current → return`（状态相同不写）对应物不存在，要自己在执行器写

### 4. 速率限制：没有

- grep `services/appfunctions` 全目录：无 throttle / ratelimit / burst / idempot 任何命中
- 唯一时间机制是 5s 取消超时（不是限流）
- 顺带防误读：`SettingsState.java:110-111` 有 200ms/2000ms 写合并 debounce 常量——那是磁盘写合并，不是行为闸

## 六、额外机制（RoleManager 等）

### 1. RoleManager：管「谁是默认助手」，是单席位闭集

- `RoleManager.ROLE_ASSISTANT` 存在且被消费：`VoiceInteractionManagerService.java:349` 注册 role holders changed 回调（`mRoleObserver.onRoleHoldersChanged(RoleManager.ROLE_ASSISTANT, …)`）
- 助手选择持久化在 `Settings.Secure.VOICE_INTERACTION_SERVICE`（`:587, :791, :889, :902`）
- 服务 API 全程 `ACCESS_VOICE_INTERACTION_SERVICE` 权限门（`:1334, :1477, :1488, :1505` 等）
- 含义：**助手席位 = 用户在设置里选的那一个**，系统只绑定选中者。和我们注册默认助手直接相关：走 ROLE_ASSISTANT/voice_interaction_service 是平台正式入口；`AppFunctionManager.java:79-86` 的官方示例场景就是 assistant 调 app function

### 2. SettingsProvider 写入硬闸：挡第三方，不挡我们自己

- Secure/Global 变更：`enforceHasAtLeastOnePermission(WRITE_SECURE_SETTINGS)`（`packages/SettingsProvider/src/com/android/providers/settings/SettingsProvider.java:1545, :1830`）
- **但这个闸挡的是第三方 app，挡不住持有 WRITE_SECURE_SETTINGS 的特权助手进程本身**——小米四段闸存在的理由正是「模型在自家特权进程里跑」，平台权限闸对自己的模型无效。所以四段闸不能指望平台权限层替代

### 3. 其他闭集能力面：未发现

AppFunctions 之外没有通用「能力表 + 查表 + fail-closed」机制。ContentProvider/Intent 层无对应物（Intent 是开放面不是闭集）。

## 七、四段对照总表

| 小米那段 | AOSP 对应物 | 能不能直接用 | 差在哪 |
|---|---|---|---|
| ① 表达层闭集（枚举指令 + 语义化动作 + 无通用写） | AppFunctions 调用面 = 包名+functionId+GenericDocument，协议无「写任意 key」形式；声明制闭集（注解→XSD→AppSearch 索引） | **机制直接用**；语义词汇表自己设计 | 平台无统一动作枚举（小米 URN 词汇表对应物不存在）；执行期参数不校验（XSD 有类型但没接进执行闸）；小米有云端 DDF 扩充面，AOSP 无 |
| ② 能力表校验（actionMap 查表，不在即删） | AppSearch documentId 查表：非 TRUSTED 路径查不到 → ERROR_FUNCTION_NOT_FOUND(1003)；TRUSTED 路径 → ERROR_SYSTEM_ERROR(2000) 带消息；enabled 状态校验；per-function restrictCallers；索引侧 maxAppFunctions/maxDocumentType 上限 | **直接用**（这套就是为「跨 app 动作编排」造的） | 失败语义更响（返回错误 vs 静默删队列）；TRUSTED 调用者的 not-found 错误码不精确（毛边） |
| ③ 执行器无 default（URN→专用方法，无兜底写） | 框架精确路由 + 零平台执行路径；执行器只能被 system_server 调（BIND_APP_FUNCTION_SERVICE 双向验证）；onExecuteFunction 抽象方法 | **框架部分直接用**；App 内 switch 纪律自己写 | onExecuteFunction 是自由代码，框架不禁 default——「无 default 写」是应用侧纪律，AOSP 不代管 |
| ④ 幂等 + caller tag 审计 | statsd atom（uid/错误码/大小/延迟，**无 functionId**）+ callingPackage 透传给执行器 | 审计可用 statsd 但粒度不够；其余没有 | 幂等（状态比对）、写入来源串、行为限流/熔断：**全部自己写** |

## 八、我们还要自己写什么

**AOSP 已给**（≈小米② + ③框架侧 + ①机制骨架）：能力面声明与索引、查表 fail-closed、per-function 调用者收窄、enabled 开关、精确路由与绑定、执行器身份验、取消/超时/进程死亡保险、uid 级遥测。**如果 dsh 的 Android 侧执行器走 AppFunctionService，以上全部白嫖。**

**要自己写的（按优先级）**：

1. **语义词汇表**：函数集设计——设置类用语义化 functionId（`get/switch` 成对），**绝不声明通用写函数**（AOSP 平台层没有通用写原语，我们也不能自己造一个）
2. **执行器内显式 switch、无 default**：`onExecuteFunction` 按 functionId 分发，认不出的一律拒绝——小米③纪律，代码在 App 侧
3. **执行期参数校验**：平台不校验 GenericDocument，执行器自己按声明 schema 验参数类型与缺参
4. **幂等层**：写入前读现值，状态相同不写（防重复执行刷屏——2026-11-12 事故 `svc power stayon` 43 次正是缺这个）
5. **caller tag**：写入时拼来源串进我们自己的 action log（statsd 没 functionId、没来源串，满足不了审计需求）
6. **行为熔断/绕过计数**：AOSP 无限流无熔断；statsd 只有 uid 级，按 functionId 计数要自己写（前置实证 §二.3 的「绕过熔断 idea」依然成立，且 AOSP 侧同样没有）
7. **错误处理按消息不按码**：not-found 在两条路径错误码不同（1003 / 2000+消息），我们的调用层判断用消息

**不值得抄的**：AICR 的平台签名权限（我们拿不到）；云端 DDF 下发通道（我们没有云端管控面，闭集纯本地——AppFunctions 的索引本来就是纯本地，这点反而对齐）。

## 十、我的疑问

1. 【技术】XSD 的参数类型已经进了 AppSearch schema，AOSP 是否有计划把它接进执行期校验？——若有，①的参数闸就白嫖了；若无，我们的执行器自己校验时可以直接读 schema（AppSearch 查询元数据），省得重复定义
2. 【实现毛边】TRUSTED 调用者的 not-found 落 ERROR_SYSTEM_ERROR(2000) 而非 1003——有意（对 TRUSTED 调用者隐藏存在性？）还是顺手漏的？影响我们错误处理约定，不影响闸本身
3. 【架构选择】dsh 执行器走 AppFunctionService 还是自有 ContentProvider？AppFunctionService 白嫖②③框架侧，但要求完整声明链（SDK 注解→XSD→索引）；自有 provider 则闸全要自己搭。**倾向 AppFunctionService**——本轮已证它就是把小米四段闸的机械结构做成了系统服务

## 踩坑记录区

1. **预下载文件先验头再信**：`RoleManager.java` 打开是乱码、mirror 版只有 14 字节——上次 fetch 失败的残骸被当成「已下好」材料直接进了任务书。同族坑：QQ 缩略图 `_720.png` 实为 jpeg（feedback 已有）。避法：拿预置材料先 `head -c 200` 验格式再开工。
2. **Git Bash 的 /tmp ≠ C:\tmp**：curl 落盘到 `/tmp/aosp-fetch/`，用 Windows 路径 `C:\tmp\...` 去 Read 读不到；`cygpath -w /tmp` 解出真身是 `C:\Users\<user>\AppData\Local\Temp\`。避法：要么统一用 cygpath 解析，要么直接落已知 Windows 路径。
3. **①②同一张表，应验**：AOSP 的执行校验表（AppSearch apps-db）就是声明闭集本身——发现（文档检索）和执行校验（documentId 查表）共用一张表。任务书预判的两处坑一个没漏。
4. **类名陷阱，应验**：`AppFunctionManagerService(Impl)` 名字最响但只有编排；真闸在 `CallerValidatorImpl.verifyCallerCanExecuteAppFunction` 的 documentId 查表 + `AppFunctionManagerHelper.isAppFunctionEnabled` 联表查询。校验层结论必须给到方法级行号，不能停在类名。
5. **错误码毛边**：not-found 有两条路径两个码——非 TRUSTED 走 `ERROR_FUNCTION_NOT_FOUND(1003)`（CallerValidator 查表 → AppSearchException NOT_FOUND 映射，Impl:498-499），TRUSTED 走 `ERROR_SYSTEM_ERROR(2000)`+消息 "App function not found."（Helper:161-170 空结果抛 IllegalArgumentException，Impl:474-489 落默认码）。抄的时候按消息判，别按码判。
6. **googlesource 间歇 HTTP 000**：同一域名先通后断，curl 失败先重试/换源再下结论；本地 shallow clone 覆盖了 90% 需求，别急着全走网络。
7. **`wc -l` 在 ls 里认错列**：`ls -la` 的 owner 是中文用户名时列错位（乱码挤位），size 列容易看串——验文件大小直接 `wc -c` 或 `head -c`，别数列。
