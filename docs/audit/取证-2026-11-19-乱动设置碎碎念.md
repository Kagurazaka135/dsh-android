## 摘要

**核心局限，先说在前面**：agent 的碎碎念本体（thinking / 正文）在私有目录 `/data/user/0/com.deepseek.harness/files/payload/dshhome`（路径由 heal-ledger 旁证），三重锁（非 debuggable / SELinux untrusted_app_27 / su 不存在）全部够不到。auditd 只记「什么进程碰了什么对象」，**不记命令参数，更不记模型说的话**。所以本报告能证明引擎今天跑过 rm×5、mkdir×2、rish×16、ip×4（被拒）、cp×35、git×19，但**拿不到这些命令前后模型的原话**——这正是任务书要的主菜，缺了，缺的原因和下次怎么取写在「没找到的部分」。

## 踩坑记录

### 坑 1：手抄 auditd 原文导致输出退化循环，污染报告草稿
- **坑**：22:47 手写报告引用 auditd 长行时，输出退化成中英混杂的循环文本，污染草稿并落盘 14KB（22:56 时间戳）。
- **根因**：长行逐字手抄是高错误率操作；Write 工具的一次异常返回（命令与返回不匹配）可能加剧了状态混乱。
- **解法**：核实磁盘真实状态 → 删除污染草稿 → 改为程序化提取（build_report.py 从落盘证据文件读行直接拼报告）。
- **下次怎么避**：**取证报告的原文引用永远不手抄**——先把证据落盘成文件，再用脚本拼报告。写报告的脚本和证据文件分开放。

### 坑 2：668MB 日志的设备端 grep 会拖死 adb 通道
- **坑**：`grep -icE '...' /data/local/tmp/vscreen.log` 在设备端跑，420 秒超时转后台仍不出结果。
- **根因**：668MB 文本 + 设备端 CPU + UTF-8 正则（中文关键词）三重放大；adb 通道串行。
- **解法**：只拉需要的段（tail -c 30MB）回 PC，PC 侧 grep。
- **下次怎么避**：大文件取证先看 wc/头尾采样判断结构，再决定「拉回 PC 分析」还是「设备端精确提取」，别直接上全量 grep。

### 坑 3：auditd 的 app= 标签有误归属
- **坑**：`comm="ecurity.miui:ui"`、`comm=".screenrecorder"` 等系统进程的拒绝记录也带 `app=com.deepseek.harness`。
- **根因**：auditd 的 app= 字段按「触发审计的最近 App 关联」归因，系统进程的行为可能被挂到 App 头上。
- **解法**：按 scontext 二次甄别——`u:r:untrusted_app_27` 才是真 App 域，`u:r:system_app`/`u:r:platform_app` 剔除。
- **下次怎么避**：统计 comm 前先按 scontext 过滤，别拿 app= 直接当归属证据。

### 坑 4：adb pull 到中文+空格路径的目录会建出残废文件
- **坑**：`adb pull /sdcard/.../heal-ledger G:/...取证.../heal-ledger` 建出名为 `heal-ledg` 的残废目录（Not a directory 错误）。
- **根因**：adb 的 Windows 路径处理对中文+括号+空格目录名兼容差（与 cc_windows_env_pitfalls 里「adb pull 本地目标传 Windows 绝对路径」的坑同族）。
- **解法**：`rmdir` 清掉残废目录，改用 `shell cat ... > 本地文件` 重定向拉取。
- **下次怎么避**：adb pull 目标路径避开中文/空格/括号；或统一走 `shell cat > file`。

### 坑 5：logcat -t N 的「窗口」会漏掉 auditd 主体
- **坑**：`logcat -d -t 5000 -b all` 只有 16 条噪音命中；全量 dump 后有 540 条。
- **根因**：auditd 行不在最近的 5000 行窗口里（21:00–22:22 的记录被更晚的系统日志滚出窗口）。
- **解法**：全量 dump 落盘后 PC 侧 grep。
- **下次怎么避**：logcat 取证一律全量落盘再 PC 侧过滤；`-t` 只用于粗筛存在性。
