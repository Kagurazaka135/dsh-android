# 审计：小爱用什么机制挡住「模型自己玩设置」

- 日期：2026-11-22 · 执行：ZCode(GLM)
- 样本：小米 14 (houji) 国行 HyperOS **OS3.0.307.0** 全量 ROM（xiaomirom.com 官方镜像，WSL /root/romc 解包，上轮会话遗留）
- 分析对象 APK：
  - `com.miui.voiceassist`（小爱主 App）**7.12.2.0318**（product_a/app/VoiceAssistAndroidT）
  - `com.xiaomi.aicr`（**Xiaomi HyperAI Engine**，agent 动作运行时）**3.63.1**（product_a/priv-app/MIUIAICR）
  - `com.android.settings`（系统设置，agent 动作执行器之一）（system_ext_a/priv-app/Settings）
  - `com.xiaomi.misettings`（对照样本）
- 方法：apktool 3.0.3 / baksmali 2.5.2 纯静态逆向 + sysapps.bayton.org 权限交叉验证 + 官方文档/用户报告检索。未触碰真机、未安装任何 APK。
- 施工区：`G:\code\xiaoai-audit\`（smali 反编译产物、解包产物、DDF 动作清单 `ddf_all_actions.txt`）

---

## 一句话结论

**模型绕不过的那道闸在 `com.xiaomi.aicr`（HyperAI Engine）的 `ActionCoreProvider` 里：agent 动作执行前必经 ContentProvider 操作 `check_action_queue`，逐个动作调 `SpecParser.isActionSupport()`——动作 URN 不在本机能力表 `actionMap`（由 DDF 闭集构建）中，直接被判 "delete action: <urn> for action not found"，从执行队列删除，永远不会落到任何设置写入。** 且设置类动作本身全部是语义化闭集条目（`switchautorotationmode`、`switchsilentmode`……），协议里**不存在**「写任意 settings key」的表达形式。

⚠️ 但这不是唯一结论——**旧协议 `System.SetMiuiDatabase` 是客户端无白名单的通用写**（见 §2.3），它的闸在云端，APK 内不可见。诚实报告见 §1.3 与 §3。

## 一、查到了什么（按四个层次）

### 1.1 能力面定义（Q2）

**能力表不是一张表，是三层合并的闭集：**

| 层 | 内容 | 证据 |
|---|---|---|
| ① 各 App 自声明 | 35 个系统 App 在自己 AndroidManifest 里放 `meta-data com.hyperos.AI_ACTION_DESCRIPTION*` → 指向自己的 DDF（AIoT spec v3 JSON）；配 `hyperos.action.AIACTION_PROVIDER` intent-filter 的 ContentProvider 作执行器 | `G:\code\xiaoai-audit\settings_unpacked\AndroidManifest.xml:342,4160-4190`；全 ROM 扫描 35 个声明者（清单见文末附录 A） |
| ② AICR 内置 | `res/xml/aiaction_data.xml` **57 条**（context 屏幕感知/点击/滑动/剪贴板/OCR、contacts、search）+ `res/raw/*_ddf.json`（MiPhone protobuf 式 JSON：device→module→service→action，in/out 参数全类型化） | `G:\code\xiaoai-audit\aicr_unpacked\res\xml\aiaction_data.xml`；`res/raw/aicr_action.json` |
| ③ 云端 DDF | provider 操作 `get_ddf_id` / `get_ddf_file`（按 ddfid 取回 DDF 内容）/ `get_all_actions`；DDF id 存系统设置 | `aicr_unpacked/smali/com/xiaomi/aicr/hce_framework/protocol/action/com/xiaomi/aicr/actionprovider/ActionCoreProvider.smali:2062`（"ddf_file"），`:1555`（"get_ddf_file"），`smali_classes3/.../spec/d.smali`（SpecParser） |

**本 ROM 静态可数的动作 URN 下限 ≈ 196 条**（本次 dump 的 7 个 App：Settings 95 + AICR 内置 57 + MISettings 10 + DeskClock 16 + SystemUI 8 + BluetoothExtension 4 + Telecom 3 + AudioMonitor 3；其余 28 个声明者的 DDF 放置方式未逐一 dump，不计入）。**小米官方宣传的「3000 能力」在本地 ROM 静态数据里不存在对应实体**——3000 是云端 DDF 的规模口径，本地只有 ddfid 索引与增量 DDF 文件（声明 vs 实现：本地实现是「可扩充的闭集」，云端定义扩充内容）。

**设置类条目全部语义化、无通用写原语**。Settings App 的 95 条全列见 `G:\code\xiaoai-audit\ddf_all_actions.txt:36-131`，代表性条目：

```
[com.android.settings/settings/switchautorotationmode]  ← 自动旋转开关（getautorotation 成对）
[com.android.settings/sound/switchsilentmode] [sound/switchzenmode] [sound/adjustvolumepercent]
[com.android.settings/wifi/switchwifimode] [mobiledata/switchmobiledatamode] [tether/switchtethermode]
[com.android.settings/display/auto_brightness_switch] [display/set_screen_brightness]
[com.android.settings/uimode/night_switch] [settings/switchlocationmode|switchnfcmode|switchtalkbackmode]
[com.android.settings/settings/switchairphonemode]  ← 飞行模式
```

每条都是「语义动作名」，带 get/switch 成对查询。**表里没有** `settings put (key,value)`、`wm` 类通用原语。AICR 内置的通用原语是**屏幕操作**类的（`context/click_event`、`swipe_event`、`inject_text_with_focus`、`set_clipboard`），不是设置写原语。

### 1.2 模型输出格式（Q1）

云端下发的指令信封格式（小爱 App assets 里的 UI mock 数据即真实信封样例）：

```json
{"header": {"namespace": "Agent", "name": "Action", "id": "...", "dialog_id": "..."},
 "payload": {"action": ["{\"type\":\"urn:aiot-spec-v3:com.mi.phones:action:[com.android.settings/sound/switchsilentmode]:0:1.0\",\"in\":{\"enable\":true}}"],
             "silence_exe": false, "is_loading": false, "is_background": false}}
```

- 来源文件：`G:\code\ai-phone-audit\rev\miui_VoiceAssistAndroidT\assets\action_data.json`（样例查询"打开静音"）
- **指令类型是闭集枚举**：小爱 App 的 OperationFactory（`classes7/h90/d.smali` `parseSingleInstruction`，`sswitch_data_9e2` 稀疏开关）只认固定 namespace 集合：Dialog / SpeechSynthesizer / AudioPlayer / Alerts / SpeechSettings / General / **Settings** / Selector / PushTemplate / FullScreenTemplate / PlaybackController / Video / Scene / Phone / **Agent** / AutoController / Nlp / NFC / Map / GPS / Bluetooth / Speaker / DeviceBinding / BrightnessController / Network / ApplicationSettings / MultiModal / Application / Suggestion / Template。指令全名同样闭集（如 `Agent.Action`、`System.SetMiuiDatabase`、`System.Power`，见 `h90/d.smali:3700-3900`）。
- **Agent 动作内容是 URN 闭集**：URN 格式 `urn:aiot-spec-v3:com.mi.phones:action:[目标包/服务/动作名]:iid:版本`，动作名必须出现在 DDF 里，in 参数按 DDF 的类型定义校验。
- **模型无法表达「写一个表里没有的 key」**：URN 之外的自由文本不在 payload.action 的解析路径上；URI 解析失败的 URN 不在任何 App 的 DDF 里 → 在 §1.3 的 check 处被删。

## 二、关键发现

1. **挡「玩开关」的不是一个闸，是四段串联闸，每段独立成立**：
   - 表达层：指令类型闭集 + URN 闭集——模型没有「任意写」这个词汇
   - 校验层（★唯一在本地代码里可指认的硬闸）：`ActionCoreProvider` case4 → `spec/d.isActionSupport` → `actionMap`（DDF 闭集）查询，不在即删
   - 执行器层：URN→专用方法 switch，无 default 写路径；调用者必须 == com.xiaomi.aicr
   - 执行逻辑层：幂等（状态相同不写）+ caller tag 审计（"AiAction#doActionForSwitchAutoRotationMode" 进框架日志）
2. **「能力面封闭」在小米不是口号，是分布式 DDF 注册制**：每个 App 用 manifest meta-data 声明自己的动作面，AICR 扫描合并（+云端 DDF 增量）。App 不声明 = 这个 App 对 agent 不存在。
3. **小米和上一轮审计结论吻合但更细**：上轮说「四家没做拒绝后无路可走」——本次实证小米做了 check+delete（动作级丢弃），但仍**没有**绕过计数/熔断/降级（`hp/a` 与 AICR 代码里无 deny 计数器、无降级路径）——check 是「单次拒绝」，不是「行为熔断」。我们 §6.18 的绕过熔断 idea 依然成立。
4. **旧协议是缺口**：`System.SetMiuiDatabase` 客户端无 key 白名单，闸在云端不可验证。若专家模式 LLM 能触达旧指令类型（云端是否允许未知——APK 无法判定），这是理论缝隙。缓解证据：该 Operation 在 N() 失败路径统一回「暂不支持」TTS，且属性类型受 `Sys$PropertyType` 枚举约束（STRING/LONG/FLOAT/INT）。

## 四、对我们有什么用

**能抄的（按优先级）：**
1. **三段式闸结构**：表达层闭集（模型词汇表里没有"裸写"）→ 本地白名单 check（不在表即删，错误可观测）→ 执行器调用者钉死。dsh 的 Android 侧如果做「模型碰设置」，每一段都比单靠 prompt 硬。
2. **执行器侧的调用者身份校验**（`checkPermissions` 的 `getCallingUid→包名==aio运行时`）：挡「借刀」零成本——dsh 插件协议可抄「只有 harness 主进程的 uid 能调执行器」。
3. **幂等 + caller tag**：状态没变不写 + 写入带可审计的动作来源字符串。事故日志（svc power stayon 43 次）正是缺这两样。
4. **DDF 注册制**：能力声明放在每个插件自己的 manifest/清单里，运行时扫描合并——比中心化能力表好维护，且「不声明即不存在」天然默认拒绝。

**抄不了的：**
- AICR 的平台签名权限（WRITE_SECURE_SETTINGS/INJECT_EVENTS）——我们是普通 App，拿不到；dsh 走 Shizuku/无障碍的路子，权限模型不同
- 云端 DDF 下发通道——dsh 没有小米这种云端管控面，闭集只能纯本地

**行业定位更新**：小米 = 「拒绝后无路可走」四家里做得最深的一个（动作级 delete + 调用者钉死），但仍无绕过熔断。差异化空间不变。

## 踩坑记录区

1. **`strings` 默认不抓 UTF-16**：APK 里 AndroidManifest.xml 是二进制 AXML（UTF-16LE 字符串池），第一轮全 ROM 扫描 0 命中就是因为它——`strings -el` 或直接 `bytes.decode('utf-16-le')` 才对。
2. **WSL ubuntu-dify 没装 unzip**：改用 python3 zipfile。kali-linux 里上轮解的 ROM 已不在，ubuntu-dify /root/romc 还活着（31G）——**别急着重新下 4GB ROM，先翻现场**。
3. **`b6.isSettingsSwitchEnable` 名字骗人**：是值归一化不是白名单。按方法名下结论会翻车，必须读实现。
4. **apktool packed-switch 映射表是倒序的**（`pswitch_40`=case 0，case 0x25=`pswitch_1b`）：按直觉正序映射会读错分支，数错一次就找到 doActionForGetCoolFan 去了。
5. **ugrep 对二进制文件需要 `-a`**（否则计数输出为空）；Git Bash 下 WSL 调用要 `MSYS_NO_PATHCONV=1`（记忆已知，本轮再证）。
6. **apktool `--no-src` 解包快但无 smali**，主 App 23 个 dex 需 baksmali 补；直接全量 `apktool d`（AICR/Settings）更快拿到全部 smali。
7. **ROM 分区文件是 0 字节占位**（`rom/cn/product_b` 等）——上轮的真实解包现场在 WSL 里，Windows 侧目录只是空壳，别被表象骗。
