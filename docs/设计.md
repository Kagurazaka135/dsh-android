# dsh 安卓魔改 · 完整方案

> 把 DeepSeek Harness（dsh）魔改到安卓手机，做成「能喊一声的 AI 助手 + 手机 agent」。
> 薄内核 + 万物插件，PC / 手机通用。整理于 2026-10-13。

---

## 0. 目标

在原版 dsh 上做出：

- **语音助手**：唤醒词 / 录音 / 语音识别 / 语音播报 / 浮标，**锁屏也能叫**
- **手机 agent**：让 AI 真正操作手机（点屏 / 读屏 / 起应用 / 特权 shell）
- **记忆**：跨会话的分层记忆（L3 版本化事实 + L4 启动摘要 + 夜间整理）
- **万物插件**：dsh 插件生态白送，PC / 手机同一份包

**原则**：**本体保持薄**（只加一个插件管理界面），其余（语音 / 记忆 / …）全做成插件塞进去。

## 1. 总架构（三层 + 一桥）

```
┌─────────────────────────────────────────────────────┐
│ dsh 插件层（Node，纯插件，PC/手机通吃）               │
│   ① 语音编排插件   ② 记忆插件   ③ 万物插件（dsh 生态）│
├─────────────────────────────────────────────────────┤
│ 桥 call(method, params)   一行 JSON + X-DSH-Token    │
├─────────────────────────────────────────────────────┤
│ 原生层（Android，Kotlin/Java）                        │
│   woaiys3 原有：vscreen · shell · 无障碍 · 鉴权        │
│   ★ 自研新增：语音模块（麦克风/TTS/唤醒服务/浮标）      │
├─────────────────────────────────────────────────────┤
│ dsh 本体（薄内核，woaiys3 已有）                       │
└─────────────────────────────────────────────────────┘
```

**隔离点 = 桥那条线**：插件层（编排）**PC/手机通用**；桥往下的原生能力**平台相关**。

## 3. 自己做什么（四块）

### ① 原生语音模块（唯一 fork 改原生处）

**位置**：woaiys3 的 `android-app/src/com/deepseek/harness/` 下**新建 `VoiceService`**。

- **照抄它自己的模式**：前台服务 + 手搓 `ServerSocket`（模板 = `AccessibilityService`；前台保活抄 `EngineService`；浮标抄 `OverlayService`）
- **端口**：从 engine 端口派生（如 `enginePort+200`）
- **鉴权**：路由过 `LocalAuth.ok()`
- **权限**：补 `RECORD_AUDIO` + `FOREGROUND_SERVICE_MICROPHONE`
- **引擎**：sherpa-onnx —— 唤醒 `KeywordSpotter`、ASR `OfflineRecognizer` + SenseVoice
- **要抄 Luwi 的三块平台逻辑**（不依赖 dsh，最值钱）：
  1. **单路采集扇出**：一路 `AudioRecord`（16k 单声道 PCM16），唤醒词与 VAD 是它的两个消费者
  2. **半双工闸**：`forward(speaking)` 返回丢弃时，**既不喂唤醒也不喂 VAD、还把 VAD 半句作废**（否则 TTS 停了拼成"前半+后半"）
  3. **`talking()` 尾巴预算**：系统 TTS 的 `onDone` 常早报，要加"按字数估的预算 + `isMusicActive`"才算真说完

### ② 桥的语音原子接口（唯一要动脑处）

**复用 woaiys3 的桥范式**（HTTP 路由 + JSON + `X-DSH-Token`）：

```
/voice/record     开麦          /voice/recognize   调 ASR
/voice/stop       停麦          /voice/tts         播报
/voice/wake       唤醒服务开关   /voice/event       长轮询/SSE 唤醒事件
```

- **插件侧**新建 `dsh-tool-voice`（**照 `dsh-tool-accessibility` 骨架**）
- `env.put("APP_VOICE_PORT")` 在 `spawnNode` 里注入
- **桥够原子 → 上面才能纯插件写**，且语音层可独立替换

### ③ 语音编排插件（纯 Node）

- "唤醒 → 开麦 → ASR → 进 dsh → 拿回答 → TTS"，**照 `lw_voice` 设计**：
  - 一轮只收**一句**，说完 10 秒关链（视频模式才常驻）
  - **语音有自己的会话**（别插进主会话）
  - **命令句被吃**（"打开视频模式"等）
- **dsh 侧对接**：识别 ≡ 实现一个 **`SpeechProvider`**（`{ info, transcribe(input, signal) }`）→ `ctx.speechToText.register()`，**白嫖 dsh 整条 seam 链**（Remote + UI + 准备进度）
- **TTS**：dsh **完全没有**（文档明说）→ 照 `SpeechToText` **再开一个新 seam** `ctx.speechSynthesis`

### ④ 记忆插件（**纯插件，零原生**）

- **已独立成库**：见 `G:\code\dsh-memory\设计方案.md`（L3 版本化 + L4 摘要 + 夜间整理）
- 与本方案正交：记忆管"上下文管理"，语音管"输入输出通道"，在插件层各占一个插件

**插件管理界面** → 抄 woaiys3 控制台（插件开关页现成）。

## 4. 关键设计原则（铁律）

1. **插件编排通用、桥平台相关** —— 隔离点就在"桥"这条线
2. **定时归 host、插件只注册不自持** —— 用 dsh 原生 `schedule_create` 外部踢；插件 `apply` 时**幂等自动注册**；只有"高频 + 不需模型"的机械动作才内置（`setInterval` host 重启即丢 + 自动化页看不到）
3. **记忆只追加不删** —— L3 版本化天生安全；L2 衰减只出建议
4. **模型一律走 broker** —— `http://127.0.0.1:9999` + 假 key `local-broker`，代码零真 key

## 7. 待决策 / 风险

### 7.1 语音路线 A vs B（**动作最大**）

| 路线 | 做什么 | 代价 |
|---|---|---|
| **A 贴 dsh 原生** | 只写一个 `SpeechProvider`，录音用 WebView `getUserMedia` | **最省**，但**只有"点一下说话"，无唤醒/锁屏** |
| **B 自研原生** | 自研 `VoiceService` + 唤醒常驻 + 浮标，桥到插件 | 工作量大，但**喊一声/锁屏/打断都有** |

> TTS **无论哪条路都得自己做**（dsh 完全没有）。

### 7.2 底座 woaiys3 vs Luwi（已被 A/B 吸收）

- 若选 **A**：woaiys3 稳妥（语音小、工程成熟）
- 若选 **B**：要"翻译 Luwi 的 Kotlin 语音层到 Java"——**这跟"新写一个纯 Java 语音服务"工作量相当**，woaiys3 仍可选（它的语音从零加）

### 7.3 其他待验

- **普通插件能否直调 `ctx.schedule`**（决定"自动注册"怎么写，见记忆插件方案 §7）
- **sherpa-onnx 官方 AAR 是 Kotlin + androidx** → 两条破法：（a）接受 `kotlin-stdlib`（不写 Kotlin 源码）；（b）**手写 ~6 个 Java shim 直绑 `.so`**（JNI 是标准命名约定，可行）
- **fork 活跃项目**（woaiys3 还在更）→ 尽量"新增模块 + 插件"、少动核心，便于跟上游；语音模块做独立，真不行提 PR 给上游
