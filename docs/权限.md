# AI Agent 权限机制审计与 dsh-android 的权限方案

> 2026-10-27。审计对象：Codex / Claude Code / opencode / ZCode 以及本项目自身。
>
> 给 dsh-android 设计"防止模型做出用户没授权的动作"这套东西时，先看清楚已经有人走过的路。
>
> **结构**：机制对照（二）→ 失效模式（三）→ 可移植性清单（四）→ 本项目现状（五）→ 我们的方案（六）。

---

## 一、为什么做这个审计

dsh-android 让 LLM 通过无障碍和 Shizuku 真正操作手机——点屏幕、改系统设置、执行特权 shell。这些能力在**别的 agent 上都不存在**，所以没有现成答案可以抄。

但"要不要问用户""怎么问"这两个问题，所有 agent 都遇到过。这份审计是去别人的答卷上找题眼。

一条前置结论，后面所有内容都建立在它上面：

> **桌上所有 agent 都在优化"怎么让人看得更仔细"，而真实的失效点是"人根本不看"。**

这不是推测，是有实验支撑的：

- **HP Labs 2011《Are you sure? Yes. Oops!》**：确认对话框太常见，常见到我们已经训练自己不加思考地点过去。
- **CHI 2010《Trained to accept?》**：8 万真实用户、2×2×3 变体。用户被规训到机械接受；**对话框越像 EULA，接受得越快**。
- **SOUPS 2014《Harder to Ignore?》**：让被试反复看同一个弹窗后偷改字段——**注意到变化的人少了三分之二**，反应时间中位数只增加 **10 毫秒**。
- **SOUPS 2019《Fog of Warnings》**：对普通通知的习惯会**泛化**到从未见过的安全警告。所以"把确认框做得不一样"救不了。

## 二、机制对照

| | 默认 | 审批密度 | 核心机制 |
|---|---|---|---|
| **dsh（本项目）** | 无闸 | **0** | 见第五节，基本是空的 |
| **ZCode** | 完全访问 | **0 次** | 有六档模式，实际全部旁路 |
| **Codex** | on-request | **极高** | 先沙箱、越界才问 |
| **Claude Code** | Manual | 高 | 规则白名单 + 六档模式 |
| **opencode** | `*: allow` | 低 | 配置驱动的 permission 表 |

### Codex

**五档审批**：`untrusted / on-failure(已弃用) / on-request / granular / never`，默认 `on-request`。用户面只暴露三个 preset：Read Only / Default / Full Access。

**默认策略是"先沙箱、越界才问"**——沙箱内非危险命令直接跑，不弹窗。只有需要提权、网络被拦、或命中 `dangerous` 才问。而 `dangerous` 极窄：Unix 只有 `rm -f` / `rm -rf`，Windows 只有 `del /f` / `rd /s /q` 一类。

**沙箱**：macOS 用 Seatbelt（`(deny default)`）；Linux 用 bubblewrap + seccomp；Windows 用受限令牌 + ACL + WFP。网络默认全平台禁用。

值得抄的：**拒绝熔断**——连续 3 次或近 10 次被拒批即中断本 turn。这是治"模型反复试"的结构性手段。

值得警惕的：**弹窗默认项是 `Yes, proceed`，回车即批准**。防"没看"只做了一半（正文给完整命令、后台标题闪烁提示、失焦发通知），但没有强制延迟、不要求输入关键词。

已知问题（公开 issue）：按 basename 判安全导致路径限定命令被放行；hook 拒绝后可借"retry without sandbox"绕过；**审批弹窗过多导致用户被迫批量点同意**。

### Claude Code

**六档模式**：`default`(Manual) / `acceptEdits` / `plan` / `auto` / `dontAsk` / `bypassPermissions`。

其中 `plan` 模式的做法最值得注意——**它不是靠提示词，是靠执行器拦截**：

> Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source.

"不能改"是**模式状态机 + 单一放行闸门**，不是让模型自觉。这一点对本项目直接适用。

**规则求值顺序固定 `deny → ask → allow`，且窄 allow 挖不出宽 deny 的口子**——`Bash(aws *)` 拦得住 `Bash(aws s3 ls)`，不管后者规则写得多具体。

**官方自己承认 Bash 规则不是安全边界**：`Bash(curl *)` 拦不住 `/usr/bin/curl`、`sh -c 'curl ...'`、`git -C . push`。真正的边界要靠沙箱，而 **Windows 原生平台上没有沙箱**。

已知问题：桌面版曾把主按钮改成 "Always allow"、把 "Allow once" 藏进下拉，导致用户下意识按回车永久授权了没打算给的东西。

### opencode

**默认 `"*": "allow"`**——不配置的情况下最松。只有 `external_directory`、`doom_loop`、`.env` 默认 ask（文档说 `.env` 默认 deny，与代码不符）。

但它有两个设计明显优于其他家：

**一、"总是允许"不持久化。** 授权只持续到进程重启，不落盘。对比 Claude Code 把"别再问"永久写进配置文件——这正是白名单随时间无限膨胀的成因。

**二、`doom_loop` 检测**：同一工具、同一输入、连发 3 次即弹窗。这是**唯一一个不靠"动作危险程度"而靠"行为模式"的判据**，对长任务特别有用。

另外它的 pattern 由工具自己算出（bash 用 tree-sitter 解析后取命令前缀），不是用户手写通配；reject 时可带文字反馈回灌给模型。

### ZCode

机制其实齐全：六档模式（default / build / edit / plan / guarded / yolo），弹窗有"允许一次 / 允许本会话 / 始终允许本项目 / 始终允许此命令 / 拒绝"，还有"完全访问"。

但对一台日常使用的机器做本地统计后，结论是：

> **机制齐全，实际被「完全访问」整体旁路——不是确认了没人看，是一次都没确认。**

一台真实机器上的数据：80 余个会话里 77 个处于完全访问；近 7000 条工具调用中，**审批状态字段全部为 `none`，审批事件一次都没发生过**。

配套的两个发现更要命：

1. **应用主动降低用户戒心**——空闲时段提示"建议权限切换为完全访问，以减少任务失败率"。
2. **行为守则是提示词级的，且守则文件本身可被 Edit**。要求"某目录只读"的约束，在完全访问模式下等于没有。

## 三、失效模式

五家看下来，失败的位置各不相同，但方向一致：

| 家 | 失效点 | 表现 |
|---|---|---|
| ZCode | 从不问 | 审批事件 0 次 |
| Codex | 问太多 | 用户被迫批量点同意 |
| Claude Code | 问得密但被绕过 | 白名单静默膨胀；硬检查绕过规则系统 |
| opencode | 默认放行 | 不配置就是全开 |
| dsh | 闸是假的 | 见第五节 |

**三个可以提炼的结论：**

### 1. 假阳性率决定闸门生死

弹窗十次有九次是无害的，人就会学到"弹窗 = 噪音"，第十次也不看。**杀死权限系统的不是用户懒，是系统训练出了"弹窗即噪音"。**

推论：频率会抵消。`成本 ∝ 频率 × 摩擦`，`收益 ∝ 频率 × P(危险) × 损失`——**频率自己消掉**。"少弹一点"救不了这道闸，只有降低假阳性率能改。

### 2. 门槛高不会让人不开，只会让人偷偷开

把关闭开关藏起来、抬高门槛，危险的事并没有减少，只是从明处挪到了暗处。

一台机器上的实测：通过逐个点"别再问"累积出的 610 条授权规则里，包含了几条组合起来等价于任意代码执行的宽泛规则，以及一个真正的付费动作。**这在功能上就等于"完全访问"，但它是不可见、不可回顾、不可管理的版本。**

> 安全设计的失败往往不在"管得松"，在"可审计性"。
> 管得松但看得见，是可以管理的；管得紧但被绕开，你不知道它已经松成什么样了。

### 3. 确认本身救不了，因为前提是错的

如果默认"人会看"，所有设计都在优化"怎么看得更仔细"——组合键防反射、位置漂移打断肌肉记忆、理由写详细。

但真实前提是"人不看"。那么优化目标就不该是**让人看**，而该是**让不看也不出事**。

位置漂移是这条的反面证明：它确实让人无法形成肌肉记忆，但代价是"没看但手按了"——**从"每次都点允许"变成"随机点到允许或拒绝"，安全性没提升，摩擦翻倍。**

## 四、哪些能搬

### 能直接用

| 设计 | 来源 | 为什么适合手机 |
|---|---|---|
| **`deny > ask > allow` 固定优先级** | Claude Code | 不依赖模型自觉，不依赖文本解析。先立几条硬 deny，后续怎么点允许也冲不破 |
| **`doom_loop` 检测**（同工具同输入连发 3 次即问） | opencode | 唯一的行为模式判据，对上百步的长任务特别有效 |
| **拒绝熔断**（连续多次拒批即中断本 turn） | Codex | 治"模型反复试" |
| **"总是允许"不落盘** | opencode | 权限面不随使用时间单调膨胀 |
| **reject 时可带文字反馈回灌模型** | opencode | 比单纯点 No 有信息 |
| **危险态可见**（橙色 + 警告图标 + 当前状态常驻显示） | ChatGPT 桌面版 | 让人至少知道自己在裸奔 |

### 改造后用

| 设计 | 来源 | 改造点 |
|---|---|---|
| **plan 模式靠执行器拦截** | Claude Code | 手机版的"只能聊天"不能写在提示词里，必须**执行器层不注册那些工具** |
| **三档语义（只读 / 工作区 / 全权）** | Codex | 手机的"只读"不存在——任何点击都可能有副作用，得分"可逆 / 不可逆" |
| **风险 × 授权等级矩阵** | Codex | 概念可用，但要按手机的**动作语义**（点哪个元素、发给谁、改什么）而非命令前缀判定 |

### 搬不了

| 不能搬的 | 原因 |
|---|---|
| **一切进程沙箱**（Seatbelt / bwrap / WFP） | 都假设有子进程。无障碍和 Shizuku 的动作发生在系统里，没有子进程模型 |
| **workdir / 写根边界** | 手机没有"项目目录"这个天然边界，一次 tap 不落在任何路径里 |
| **"命令 + 前缀"作审批单元** | 手机动作是"点了哪个元素、填了什么、发给谁"。按坐标点同一个按钮可以被滚动、无障碍别名、同义入口无限绕过 |
| **单命令超时** | 手机动作没有"命令"这个粒度 |
| **网络开关** | Android 的网络权限是 per-app，不是 per-action |

### 手机比桌面更危险的地方

1. **没有"只读档"**——桌面上 `ls` 是纯读；手机上任何点击都可能有副作用。
2. **兜底少一层**——桌面上文件错了能 git 回滚；手机上的动作不可撤销。

最根本的不对称：

> **PC 上搞砸了留在你硬盘上；手机上搞砸了往往已经发出去了。**

## 五、dsh 的现状

本项目自身的权限面，实测下来是负分：

**48 个工具，没有一道真的闸。**

| 插件 | 工具数 | 审批相关代码 |
|---|---|---|
| `dsh-tool-accessibility` | 10（tap / swipe / type / gesture / screen…） | **0 行** |
| `dsh-tool-vscreen` | 8 | **0 行** |
| `dsh-tool-voice` | 8 | **0 行** |
| `dsh-tool-browser` | 10 | **0 行** |
| `dsh-tool-android` | 7 | 9 行（默认关） |
| `dsh-tool-shizuku` | 5 | 4 行（默认关） |

三个具体问题：

1. **危险动作白名单是死代码**——定义之后全文件再无引用。
2. **闸门指向一个不存在的服务**——`maybeApprove` 调用 `ctx.get("approval")`，而宿主根本没有注册这个服务。打开对应开关的后果不是"有保护"，是**所有过闸工具直接报错罢工**。这个开关从写下那天起从未被真正执行过，所以也没人发现它是坏的。
3. **分类错**——过闸的是纯读操作，本该由白名单管的写操作反而没被分类。

**比"没有保护"更糟的是"看起来有保护"**：后续接手的人看到 `maybeApprove`，会以为已经有人管了。

## 六、我们的方案

### 6.1 核心前提：手机上「人类确认」是失效的

桌面上，「人类确认」成立，是因为 **agent 和人是两个物理上分开的通道**——模型只能操作文件，人只能操作键盘鼠标，模型碰不到那个回车键。

**手机上没有这个分离。agent 用的就是那只手。**

`adb input tap` 注入的事件，在 App 层和真实触摸是同一个 `InputEvent`，同样的 source、同样的坐标。普通 App 无法区分。

所以前面审计的四家，它们的「确认」设计在手机上都少了一个隐含前提。它们没考虑过，**因为桌面上不存在这个问题**：Codex 防的是「用户不看」，Claude Code 防的是「规则太宽」，没有一家防过「模型自己点确认」。

> **手机上真正的「回车即批准」，是模型自己点自己。**

整个第六节都在回答一个问题：**在一个 agent 和你共用同一只手的环境里，怎么保住「确认」这两个字的意义。**

---

### 6.2 四条设计原则

**① 能拦在「它做不到」，就别拦在「问你要不要」。**

结构能解的问题用流程解，只会制造摩擦。如果 bash 本来就没有发消息的能力，那它跑一万次脚本也不需要确认。

**② 假阳性率决定闸门生死。**

弹窗十次有九次无害，人就会学到「弹窗 = 噪音」，第十次也不看。杀死权限系统的不是用户懒，是系统训练出了「弹窗即噪音」。

**③ 需要人看的东西，默认会被花掉。**

所以优化的目标不是「让人看得更仔细」，而是「不看也不出事」。事后通知之所以有效，是因为它是**结果**不是**问题**——人对自己没做过的事有天然警觉，对「要不要做」的弹窗没有。

**④ 能力放开的正当性，来自「出了事能收拾」。**

权限尽量开，靠还原和审计兜底，而不是靠拦住不让做。

---

### 6.3 第一道：工具层互斥锁

模型不能直接调 Android API，只能调工具。这是唯一的着力点。

```
确认框弹出
  → 工具层进入「等待人工确认」状态
  → 期间所有能影响屏幕/系统的工具直接返回「等待确认中」
     （android_tap / android_swipe / android_type / android_gesture
       / shizuku_shell / android_setting put / android_package …）
  → 人确认 → 解锁
  → 超时   → 自动拒绝，解锁
```

**这在模型视角是完全可靠的**——它没有绕过工具直接调无障碍的通道；Shizuku 也不行，`shizuku_shell` 本身也是工具。

⚠️ **实现约束**：冻结判定必须**状态驱动**，不能靠每个工具自己检查。默认全部冻结，由确认服务统一发 token，工具执行前校验。否则只要有一个工具漏了检查就漏了。

⚠️ **超时必须有**：人放下手机走了，工具层不能永久锁死。超时 = 自动拒绝 + 解锁。

---

### 6.4 第二道：让确认界面读不到、看不见

| 机制 | 挡住什么 |
|---|---|
| 整窗口 `importantForAccessibility="no"` | 无障碍**读不到任何结构**——连「这里有三个按钮」都发现不了 |
| `FLAG_SECURE` | 截图是黑的，`android_screenshot` / `android_screen` 拿不到画面 |

已核实（Nightwatch Cybersecurity，有 POC）：**FLAG_SECURE 挡不住无障碍点击**，它只防 MediaProjection 录屏和截屏。所以这两条挡的是「读」不是「点」——点击要靠第四道。

**读不到 + 看不到**，模型就只能盲点坐标。

---

### 6.5 第三道：认出「这是机器点的」

这是整套方案里唯一给出**确定性信号**（而非概率）的一道。

**MotionEvent 层面的判据**（CN-SEC 对 vivo 真机的对照实验）：

| 特征 | 真人点击 | ADB 注入 |
|---|---|---|
| `getPressure()` 抬起时 | 1.0（随硬件） | **0.0** |
| `getSize()` 按压面积 | **带小数、每次不同** | **恒为 1.0** |
| `getDownTime()` vs `getEventTime()` | 有几十~上百 ms 间隔 | **完全相同** |
| `getDeviceId()` | 物理设备 ID | **0** |

最后一条最硬，Android 官方文档原文：`An id of zero indicates that the event didn't come from a physical device`。

**无障碍层面的判据（更关键）**：`performAction(ACTION_CLICK)` **不产生 MotionEvent**，它直接调 `View.performClick()`。

```
performClick() 被调用 → 回查此前有没有触摸事件序列
                      → 没有 = 无障碍点的，不是手点的
```

**这条直接堵死「模型用 android_tap 点自己确认框」的路径**，且不需要硬件支持。

⚠️ **不能硬编码固定值**：不同厂商硬件压力基线不同（实测 vivo 为 1.0，部分友商不是固定值）。判据要用**相对特征**——面积**完全没有波动**、按下与抬起时间**完全相等**，这两个人手做不到。

⚠️ **`sendevent` 可绕过**（直接写 `/dev/input/eventX` 构造事件序列），但需要 **root**；Shizuku 的权限是 shell 不是 root，所以 `input tap` 与 `performAction` 两条主路都能拦住。

**连点三次作为补充**：人误触不会连点三次，连点三次的机器会暴露自己。判据看**方差不看次数**：

```
三次间隔 312 / 287 / 340 ms  → 人（标准差 ~27ms）
三次间隔 300 / 300 / 300 ms  → 机器（标准差 0）
```

| 间隔标准差 | 判断 |
|---|---|
| < 5 ms | 几乎肯定是脚本 |
| > 30 ms | 正常人手 |
| 5–30 ms | 结合 `size` / `pressure` 一起看 |

⭐ **命中后的价值 > 拒绝本身**：检测到的是「有程序在尝试自动点击确认」——这是一个**结果**而非问题，告诉用户比静默拒绝有用得多。

---

### 6.6 第四道：提示走人能做到、模型读不到的通道

如果提示是屏幕上的文字，无障碍也读得到——**模型和人拿到同一个信息**，那前面几道就白做了。

| 通道 | 模型能不能读到 |
|---|---|
| 屏幕文字 | **能**（除非整窗口 `importantForAccessibility=no`） |
| 通知栏 | 能（多数无障碍服务可读通知） |
| **语音播报（TTS）** | **不能** |
| **震动节奏**（1/2/3 下） | **不能** |
| 外接手环震动 | 不能 |

**语音和震动这两个通道本项目已经有了**（`VoiceService` 带 TTS，设备本身有振动马达），不需要新造。

---

### 6.7 为什么不直接用生物识别

生物识别确实是唯一物理不可模拟的信号（指纹 / 面容走设备后端认证，adb 伪造不了）。但作为**日常**确认太重——高频交互场景下每次都要求指纹，体验上等于把助手废掉。

**定位：留给最敏感的一档，作为最后一道。**

---

### 6.8 权限按「触发通道」分级

分级依据不是动作危险度，而是**这次请求有没有可能是误触发**。

| 触发方式 | 权限 |
|---|---|
| **语音** | **只能 chat**（误唤醒不可能产生动作） |
| **文字** | 发消息 / 删除 / 安装应用 → **弹窗** |
| **文字** | 写脚本 / 搜索 / 爬取 / 切应用 / 调非敏感设置 → **完全权限** |

**理由：语音是唯一可能被「非你」触发的入口**（误唤醒），文字必须人亲手打。

⚠️ 这条是整套方案的**主干**，后面几节都是给「完全权限」这一格补边界。

---

### 6.9 第三维：同一个动作，在不同 App 里语义不同

前面 6.8 按**触发通道**分级，6.9/6.10 按**动作**分级。但还差一维：

**同一个 tap，在浏览器里是导航，在微信里可能是把一句话发出去。**

所以敏感度是「**动作 × 前台 App**」的二维叉乘，不能只看动作。

| | 普通 App | 通讯类（QQ / 微信） | 金融类（支付宝） |
|---|---|---|---|
| **读屏**（`android_screen` / `android_see`） | ✅ | ✅ | **❌ 默认拒，需单次授权** |
| **点击 / 滑动** | ✅ | ✅ | ❌ |
| **输入文字** | ✅ | **⚠️ 弹窗（展示待输入内容）** | ❌ |
| **发送 / 支付 / 转账** | — | ❌ 结构禁止 | ❌ 结构禁止 |

**通讯类的「输入」：只加一个弹窗，别一刀切**

真正不可逆的是发送，但"点哪里"没法拿来判定——**同一个位置，打完字后是发送键，没打字时是别的功能**。

不过不必因此禁掉整条链路：**给输入加一次确认就够了**。这样"看看群里说了什么""翻到那条消息"全部可用，"帮我回条消息"要人确认一次，而真正发出去仍然拿不到（收件人只能人给）。

⚠️ **弹窗必须出现在人正看着的那块屏幕上。** 弹在 dsh 自己的界面里没用——人此刻正在微信里。用 `SYSTEM_ALERT_WINDOW` 浮在输入框上方。dsh 已有该权限。

⭐ **弹窗必须原样展示待输入的文字**，否则它又是个空框。展示之后就变成「**预览一条即将发出去的内容**」——人能判断说得对不对、有没有风险。**这才是值得人看的东西。**

这个设计顺带补两个洞：
1. **输入到错误输入框**（本该发群里、却点进了私聊）
2. **被注入后说出不该说的话**（内容摆在眼前，能拦住）

**在输入时确认，比在发送时确认更早也更有效**——等到发送那一步，内容已经打好了。

**为什么金融类连读都禁**

读屏的内容不是"看到了就完了"——它会**进模型上下文**（发给上游 API）、**可能写进记忆**（永久留存）、**可能落进日志**。支付宝屏幕上是余额、账单、完整卡号、身份证信息。

> **读，本身就是一个把数据送出去的动作。**

需要时用**单次临时授权**，且读到的内容标记为「不写入记忆」。

**技术判据已有**：`android_screen` 本身就返回前台应用包名，直接拿来做判定即可。

⚠️ **判定必须用系统读到的包名，不能用模型自述**。否则模型只要说"我在浏览器里"就能绕过。

⚠️ **已知绕过路径**：微信 / QQ 有网页版，用浏览器打开时前台包名是浏览器。这条目前没有干净的解法，只能靠事后审计发现（账本里记「访问了 web.wechat.com 这类域名」）。

### 6.10 通讯录与拨号：用 Intent 区分「帮忙」和「代替」

打电话是最典型的「对外 + 不可逆」——拨出去对方手机就响了，挂掉也来不及。

但不必因此只给只读。**问题不在能不能读，在读完能不能直接拨出去。**

Android 有两条路径，差别就是「帮你准备好」和「替你按下去」：

| Intent | 行为 | 危险吗 |
|---|---|---|
| `ACTION_DIAL` | 打开拨号盘、号码填好，等用户按拨打键 | ✅ 安全 |
| `ACTION_CALL` | **直接拨出去** | ❌ 不可逆 |

⇒ **结构上只提供 `ACTION_DIAL`，不提供 `ACTION_CALL`。**

> 模型可以说「号码填好了，你按一下拨打」，但最后那一下它做不到。

这条甚至不需要问用户——**落在「结构上做不到」那一层**（见 6.15）。

**通讯录本身：读可以，卡的是数据流**

读通讯录的风险不是「看到了」，是「看到的号码能变成一次拨打」。

| 能力 | 判定 |
|---|---|
| 搜索联系人（「张三电话多少」） | ✅ 允许 |
| 读取号码 | ✅ 允许，但**标记为敏感** |
| 号码填入 `ACTION_DIAL` | ✅ 允许 |
| **号码作为 `ACTION_CALL` 参数** | ❌ 不可能（没这个能力） |

**数据能流到拨号盘，流不到拨打键。**

**三个容易漏掉的入口**

1. **App 内的通话按钮**——微信语音通话、外卖「联系骑手」、客服电话，都不是系统拨号而是 App 内点击，系统层拦不到。只能靠 App 级元素匹配（`通话` / `语音通话` / `拨打`）+ 弹窗，属于启发式判据，**会有漏**。
2. **紧急号码**（110 / 120 / 119）——不走普通规则：**结构性禁止自动拨**，但允许 `ACTION_DIAL` 预填，真需要时人按一下一秒的事。
3. **误唤醒**——已被 6.8「语音只能 chat」挡住：误听到「给妈妈打电话」，最多回一句「要帮你拨号吗」，动不了手。

### 6.11 敏感名单

判据：**这个动作一旦错了，代价是用钱、时间或者道歉换不回来的。**

| 动作 | 为什么不可逆 |
|---|---|
| 对外发消息（微信 / 短信 / QQ） | 别人已经看到了 |
| 支付、转账 | 钱出去了 |
| 改锁屏 / 指纹 / 密码 / 恢复出厂 | 把自己锁在门外 |
| 给别的 App 授权无障碍 / 设备管理 | 开后门 |
| 卸载应用 | 数据跟着没了（若同步到云端，删除同罪） |

**共同点：全部是对外，或者动了容器的地基。**

内部怎么折腾都还好——改设置能还原、点错能重来、装错能卸掉。但**发出去的话收不回来，指纹改错了你进不去**。

这就是手机上最根本的不对称：

> **PC 上搞砸了留在你硬盘上；手机上搞砸了往往已经发出去了。**

---

### 6.12 「非敏感设置」白名单

必须写死，不能让模型自己判。

| 类别 | 例子 | 权限 |
|---|---|---|
| **无害可逆** | 亮度、音量、**方向锁定**、勿扰、WiFi 开关 | 完全权限 + 事后还原 |
| **影响体验** | 默认输入法、字体大小、桌面布局 | 弹窗，或完全权限 + **强制还原** |
| **改地基** | 无障碍服务、设备管理、USB 调试、开发者选项 | **弹窗 + 不可记忆** |

方向锁定属第一档：可逆、无害，给完全权限 + 自动还原即可。

---

### 6.13 下载不是一个动作，是一族动作

「下载到私有目录 → 完全权限」这个判断太粗：**下载本身可逆，但下载来的东西会被执行**。

风险不在落地，在**「落地之后会不会进执行路径」**：

```
下载到私有目录就放着        → 无害
下载后被执行 / 被 import    → 危险
下载直接进 PATH             → 最危险
```

| 下载物 | 例子 | 权限 |
|---|---|---|
| **纯数据** | 模型权重、图片、文档、音频 | **完全权限**（永不执行） |
| **代码 / 脚本 / 安装包** | `.sh` `.py` `.js` `.apk` | 下载可以，**执行 / 安装时弹窗** |
| **包管理器安装** | `npm install` / `pip install` | **弹窗** |
| **下载即执行** | `curl … \| bash` | **结构上禁止** |

**`npm install` 要单独看**：它是**隐式的下载 + 执行**（`postinstall` 会跑任意代码），是经典供应链攻击面，而 dsh 是「万物插件」系统、装插件就走这条路。折中三条：

1. 首次安装某个包时弹窗，同一个包记住
2. **默认带 `--ignore-scripts`**，需要 postinstall 的单独放行
3. 装完把包名与来源记进审计账本

**`curl | bash` 不该弹窗，该结构性禁止**：文件不落地、没有扩展名、没有审计痕迹，一条命令就是远程代码执行——绕过了所有环节。对应原则①。

**隐性通道**：下载到带执行位的目录（`$PATH` 内、`~/.local/bin`、`/data/local/tmp`）本身不危险，但给后续执行埋了引信。判据：**写到非私有目录 + 带可执行位 → 记一笔**，不拦但账本要有。

> **判据是「这个东西会不会跑起来」，不是「从哪里下的」。**

---

### 6.14 不单独确认「执行脚本」

曾经想把「写脚本」和「执行脚本」分开、执行时弹窗。这是错的。

**它把限制加在了频率最高的地方**：写代码、跑代码是一个 agent 最日常的动作，一次任务可能几十次——每次都弹，助手就没法用了。而且这正是「假阳性率决定闸门生死」自己造出来的假阳性。

脚本跑多少次都无所谓——**前提是脚本这一层本来就碰不到敏感的东西**。安全不该由「每次执行前问一句」保证，该由 **bash 工具的能力边界**保证：

| bash 能做什么 | 是否安全 |
|---|---|
| 读写私有工作区 | ✅ 随便 |
| 计算、处理数据、跑脚本 | ✅ 随便 |
| 联网下载纯数据 | ✅ 随便 |
| **发消息 / 发邮件** | ❌ 根本不给这个能力 |
| **删用户数据** | ❌ 只能在自己的工作区内删 |
| **改系统设置** | ❌ 走专用工具，不走 bash |
| **装应用** | ❌ 走专用工具，不走 bash |

推论：**如果脚本能发消息，那是 bash 工具的错，不是脚本的错**。给了 shell 就等于给了一切，那时再在「运行前问一句」根本没用——危险动作能在同一条命令里完成。真正该收紧的是 `shizuku_shell` 这类工具的能力边界。

> **敏感判定发生在「动作」层，不在「脚本」层。**

---

### 6.15 上下文绑定：续期不能被模型申请

退回安全态做成上下文绑定，不是任务结束就关——否则每次都要重新确认，无法接受。

⚠️ **最大陷阱**：如果「还在同一上下文」由模型判定，等于**模型给自己续期**，它会倾向判「在」。

所以续期必须**由客观信号驱动，且是沉默续期**：

- 不是「模型说要继续就给它」，而是「**没碰危险域就一直续着**」；一碰就自动降级重问。
- **模型没有「申请权限」这个动作可做。**

三条可靠判据：

| 判据 | 为什么可靠 |
|---|---|
| 时间窗（如 30 分钟无操作失效） | 系统计时，模型碰不了 |
| 前台 App 未离开当前场景 | 切换 App 这个动作本身可观测 |
| 未触发敏感域 | 硬分类，碰到即降级 |

---

### 6.16 尽量全开不炸：三层兜底

权限尽量放开，靠「出了事能收拾」而不是「拦住不让做」。

**第一层 · 结构上做不到**

有些事不该拦，该根本没有入口。比如发消息——不是弹窗问要不要发，而是**收件人只能由人提供**，模型手里没有这个信息。这类动作本就缺一个必要输入，不是权限问题。

**第二层 · 做得到但能还原**（量的主体，一个上百步的任务里绝大多数在此）

- 改设置 → 事前快照，事后 diff + 还原
- 改文件 → 私有工作区
- 点屏幕、滑动 → 屏幕状态本身就是结果，点错了看得见

放开它的理由：**错了看得见、赔得起。**

**第三层 · 真不可逆 → 才是弹窗**
